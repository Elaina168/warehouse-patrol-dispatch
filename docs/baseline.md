# P0 基线冻结说明

本文档用于固定当前可运行基线，避免后续模块推进时反复扩大范围或破坏已可演示链路。

## 当前基线目标

当前阶段不是从零开发，而是保护已有在线调度系统，并在此基础上继续补齐模块。

基线通过标准：

- 项目能完成正式前端构建。
- 前端单元测试通过。
- 后端测试通过。
- 固定 demo 端到端测试通过。
- 文档中的演示步骤与自动化验收保持一致。

## 固定演示场景

当前前端固定 1 个主演示场景：

| 场景 ID | 名称 | 用途 |
| --- | --- | --- |
| `integrated-demo` | 综合调度演示 | 同一场景覆盖真实仓库通道、巡检、取送、避碰、默认在线任务、作业时间与充电基础设施状态 |

共享场景 JSON 只保留 `integrated-demo`。固定回归从该场景的局部变体或独立的最小测试数据验证边界条件，不再保留额外演示地图。

`integrated-demo` 四台机器人均显式配置 `capabilities: ["inspection", "delivery", "emergency"]`，悬浮提示显示“能力 巡检 / 取送 / 突发”。旧场景省略 `capabilities` 时默认支持全部三类任务；显式字段只能使用这三个值，且不得为空或重复。主演示保持全能力车队，专业分工和唯一兼容机器人故障仅在专项回归中验证。

`integrated-demo` 使用 `26 × 16` 网格，包含12组 `3 × 2` 货架，共72个不可通行的货架实体格。每个货架有一个唯一相邻作业格，机器人不能进入货架实体格，只在作业格完成取放。货架组、顶部进货点、底部出货点、右侧机器人起点和充电口之间统一保留两个完整可走格；除固定障碍和运行时封锁外，通道与作业格可通行。

入库任务从进货点取货并送到空货架作业格；出库任务从已有货物货架作业格取货并送到出货点。默认三项配送坐标固定为：

- `T1` 入库：进货点 `[2,0]` -> 货架 `[2,4]` 的作业格 `[2,5]`。
- `T2` 出库：初始有货货架 `[13,7]` 的作业格 `[13,6]` -> 出货点 `[2,15]`。
- `T4` 入库：进货点 `[8,0]` -> 货架 `[12,8]` 的作业格 `[12,9]`。

默认演示只运行 `T1`、`T2`、`T3`、`T4`、`T5` 和 `E1`。`T3`、`T5` 分别覆盖横向和纵向通道，`E1` 在 `T=12` 释放。默认流程不追加运行时任务，不自动封锁单元，也不自动标记机器人故障。

后端会话维护权威库存和预订，并返回 `empty`、`inboundReserved`、`occupied`、`outboundReserved` 四种货架状态。`occupied` 与 `outboundReserved` 显示库存高亮；出库机器人实际到达取货作业格后货架熄灭，入库放货和作业时间完成后货架亮起。手工任务和随机任务使用同一个 `POST /api/sessions/{session_id}/tasks` 端点并执行同一套后端库存校验，前端不自行推断库存。

任务资格同时要求类型在机器人 `capabilities` 中；配送任务还要求 `robot.load >= task.demand`。当前默认、手工和随机配送任务仍使用 `demand: 1`，前端只有在车队中存在 `delivery` 能力且 `load >= 1` 的机器人时才随机生成配送任务，本阶段不扩展载重模型。在线恢复按“类型能力、配送载重、兼容机器人故障、运行时封锁、锁定、静态可达性”的顺序解释；恢复不兼容机器人不会清除任务失败，恢复唯一兼容机器人后会自动重规划。直接调度对释放时间达到未来动态触发 tick 的失败任务使用对应未来故障或封锁分类，但不提前改变当前会话状态；存在当前可执行替代时，类型或载重非法的陈旧锁会在规划前释放并立即改派。

固定流程初始有12个货架亮起；`T2` 取货后对应货架熄灭，`T1`、`T4` 放货后对应货架亮起，最终有货货架为13个。

地图显示充电口、电量和容量，但默认流程不要求进入充电状态；完整充电闭环继续由低电量专用回归验证。

## 主线 demo 操作

主线 demo 以 `integrated-demo` 为默认场景：

1. 启用避碰规划。
2. 使用在线会话；主界面固定启用场景动态机制，不提供动态事件开关。
3. 初始确认12个货架显示库存高亮。
4. 播放到 `T=12`，确认默认队列中的 `E1` 进入执行状态。
5. 观察 `T2` 到达 `[13,6]` 后对应货架熄灭，并确认 `T1`、`T4` 完成后对应货架亮起。
6. 继续播放到 `T=700`，确认6个默认任务全部完成、最终13个货架有货，且冲突、失败、截止超期和充电访问均为0。
7. 如需证明避碰价值，在同一综合场景内切换“基线对比”和“避碰规划”，确认固定输入的预测冲突由大于0降为0。

手工任务追加、运行时封锁、机器人故障及恢复属于独立扩展测试，不是默认演示步骤。

详细步骤以 `docs/demo.md` 为准。

```powershell

```

如果后续改动影响 API、算法、前端类型或演示流程，至少运行完整检查。

## 当前不做的事

P0 阶段不做以下内容：

- 不重写核心算法。
- 不引入完整 MAPF/CBS 求解器。
- 不做 3D 可视化。
- 不做营销式展示页面。
- 不引入持久化、认证或外部监控。

## 下一阶段入口

当前主线已包含 `0..5` 优先级、任务类型能力、速度、载重、电量、充电、作业时间和故障状态。`integrated-demo` 只需展示充电地块、电量和容量，不要求默认流程实际触发充电；低电量专用场景和自动化回归负责验证完整充电闭环。下一阶段入口为：

1. 继续扩展更大规模、更多随机流和复杂恢复顺序的压力证据。
2. 在单独算法分支中评估全规划时域零冲突保证与执行前安全门；二者目前未实现，也不属于任务类型能力功能。
3. 保持全能力主演示、专业分工专项回归和完整检查持续通过。
