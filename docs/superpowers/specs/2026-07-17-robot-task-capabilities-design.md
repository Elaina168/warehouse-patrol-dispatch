# 机器人任务类型能力约束设计

## 背景

当前系统支持 `inspection`、`delivery`、`emergency` 三种任务类型，但所有可用机器人都会进入任务候选集。配送任务已有 `robot.load >= task.demand` 的载重约束，而巡检和突发任务没有机器人类型限制。

本阶段需要引入异构机器人任务能力，使调度器在分配、锁定、抢占、故障接管和恢复重规划中始终遵守任务类型约束。

## 目标

- 每台机器人明确声明支持的任务类型。
- 任务类型能力是不可被距离、速度、优先级、软偏好或负载均衡覆盖的硬约束。
- 故障、封锁、锁定和无兼容机器人时的失败原因保持可解释。
- 保持历史场景、默认演示、手工任务与随机任务统一接口兼容。
- 不改变已冻结的 `integrated-demo` 执行结果。

## 能力表达

在后端 `Robot` 和前端 `Robot` 类型中新增：

```text
capabilities: TaskType[]
```

可用值严格复用已有任务类型：

```text
inspection
delivery
emergency
```

规则：

1. 字段缺失时默认支持全部三种任务，保持旧场景兼容。
2. 显式提供时至少包含一种能力。
3. 不允许重复值。
4. 不允许任务类型以外的字符串。
5. 能力是静态场景定义，不增加运行时能力修改 API，也不在 `RobotRuntimeState` 中重复存储。

## 默认场景

`integrated-demo` 的四台机器人全部显式配置为全能力：

```json
"capabilities": ["inspection", "delivery", "emergency"]
```

默认场景不通过修改能力制造新的分配差异。异构分工、专业机器人和通用备用机器人放在独立回归场景中验证。

默认流程继续满足：

- 六个默认任务在 T=700 前全部完成。
- 最终有13个货架有货。
- 冲突、失败、截止超期和充电访问均为0。
- 关闭避碰时存在预测冲突，开启避碰后预测冲突为0。

## 载重边界

现有载重字段和约束保留，但本阶段不扩展载重模型：

- 配送任务仍使用 `robot.load >= task.demand`。
- 当前默认、手工和随机配送任务继续使用 `demand: 1`。
- 默认四台机器人的 `load` 均不小于1，因此载重不影响当前演示分配。
- 不新增多级货物、体积、重量单位、多任务合并载荷或动态载重变化。
- 任务类型不兼容与配送载重不足必须分别解释，不共用含糊的错误文本。

## 统一候选判断

将机器人任务资格统一为：

```text
任务类型被 capabilities 支持
    +
若为配送任务，载重满足 demand
    =
机器人具备任务执行资格
```

后续按顺序判断故障状态、电量与充电可行性、地图可达性、时间窗、截止时间和路径冲突。

该统一判断必须用于：

- Beam Search 候选扩展。
- 场景可达性验证。
- 运行时任务定义验证。
- 任务锁定和释放。
- 高优先级任务抢占。
- 故障机器人的任务接管。
- 配送货物位置连续性与接管。
- 失败原因和恢复分类。

## 在线任务

手工任务和随机任务继续使用同一个 `POST /api/sessions/{session_id}/tasks` 端点，不增加第二套接口或任务来源字段。

处理规则：

- 场景中根本没有支持该任务类型的机器人：任务定义无效，返回422。
- 存在兼容机器人，但它当前故障或受运行时封锁影响：接受任务进入队列，通过 `failureDetails` 提供临时恢复语义。
- 随机生成器的候选任务类型限制在当前车队能力并集内，避免持续生成必然422的任务。
- 后端仍是能力验证权威，前端候选过滤不代替后端校验。

## 锁定、抢占与故障接管

- 锁定机器人能力匹配时保持锁定。
- 锁定机器人能力不匹配且存在其他兼容机器人时，释放不合法锁定并重规划。
- 高优先级任务不得抢占能力不匹配的机器人。
- 唯一兼容机器人故障时，任务暂时不可执行；恢复该机器人后自动重规划。
- 配送机器人取货后故障时，只允许支持 `delivery` 且满足现有载重约束的机器人接管，并先前往货物当前位置。

## 失败与恢复语义

任务类型能力失败按以下顺序解释：

| 情况 | 分类 | 恢复建议 |
| --- | --- | --- |
| 无任何机器人支持任务类型 | `permanent` | 增加兼容机器人或修改任务类型 |
| 存在类型兼容机器人，但配送载重不足 | `permanent` | 保留现有增加载重机器人或降低需求建议 |
| 唯一或全部兼容机器人故障 | `temporary` | 恢复兼容机器人 |
| 兼容机器人被运行时封锁阻断 | `temporary` | 清除实际阻断恢复的封锁 |
| 锁定机器人不兼容，但存在其他兼容机器人 | `temporary` | 释放锁定并重规划 |
| 兼容机器人存在但目标静态不可达 | `permanent` | 修改地图或任务目标 |

新增恢复动作值：

```text
addCapableRobotOrChangeTaskType
```

前端中文文案：

```text
恢复：增加兼容机器人或修改任务类型
```

`blockingRobotIds` 只包含恢复后确实可以执行该任务的故障机器人，不包含能力不匹配的机器人。

## 前端展示

不新增面板。机器人 tooltip 在现有电量、载重和速度信息附近增加：

```text
能力：巡检 / 取送 / 突发
```

场景导入验证 `capabilities`，导出保留字段。后端能力校验错误继续通过现有 API `detail` 显示。

## 测试设计

### 模型与契约

- 缺少 `capabilities` 的旧机器人默认全能力。
- 合法单能力和多能力组合通过。
- 空数组、重复值和未知值被拒绝。
- 前后端字段、可选性和字面量对齐。
- 场景导入导出保留能力。

### 直接调度

- 巡检、配送、突发任务只分配给对应兼容机器人。
- 距离更近、速度更快或具有软偏好的不兼容机器人仍不得获选。
- 配送任务同时遵守现有载重约束。
- 锁定不能覆盖能力约束。

### 在线调度

- 手工和随机任务继续通过统一端点。
- 唯一兼容机器人故障后任务进入临时失败，恢复后自动可调度。
- 不相关机器人恢复不得清除失败。
- 高优先级任务不得抢占不兼容机器人。
- 配送取货后的故障接管只使用支持 `delivery` 的机器人。
- `blockingRobotIds` 和恢复动作只报告真实可恢复条件。

### 基线与压力回归

- `integrated-demo` 默认结果不变。
- 完整前端构建和单元测试通过。
- 完整后端测试通过。
- 固定种子 standard 和 extended 压力集保持稳定。
- 在线压力回归保持覆盖率、冲突、失败和事件历史不变。
- 真实浏览器验证 tooltip、手工任务和随机任务。

## 实验证据

第一阶段不新增实验接口，使用现有规模对比接口传入带标签的专项场景：

- `homogeneous-fleet`：全能力车队。
- `specialized-fleet`：专业分工车队。
- `specialized-with-failure`：唯一兼容机器人故障。

对比已分配任务数、总路径长度、makespan、负载均衡、规划耗时、失败数和恢复前后覆盖情况。主界面不恢复实验面板。

## 非目标

- 不实现数字化能力等级。
- 不实现通用技能标签或熟练度。
- 不实现机器人运行时安装、卸载或修改能力。
- 不新增能力管理后台或主界面面板。
- 不改变默认演示任务和分配结果。
- 不扩展载重模型。
- 不实现全规划时域零冲突保证或执行前安全门。
- 不做 3D 可视化。

## 实施边界

建议实施顺序：

1. 数据模型、默认值、导入验证和 API 契约。
2. 统一能力判断并接入场景验证与 Beam Search。
3. 失败分类、锁定、抢占、故障恢复和货物接管。
4. 随机任务生成和机器人 tooltip。
5. 默认基线、压力回归、浏览器验证和文档同步。

本设计与当前在线任务流、统一任务接口、库存权威、充电约束和已冻结主演示兼容。
