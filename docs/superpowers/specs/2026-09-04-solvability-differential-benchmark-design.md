# 小规模可解性参照与差分基准设计

## 1. 背景与决策

当前生产规划器使用优先级时空 A*、多个机器人规划顺序、预约表和最终冲突检测。它已经能稳定处理现有综合场景和固定种子压力场景，在线安全门也能阻止顶点冲突和反向边交换冲突动作进入实际历史，但这些能力不等于完整 MAPF，也不能区分以下两种情况：

1. 场景在给定运动模型下确实无解；
2. 场景存在合法联合路径，但当前优先级规划器没有找到。

在直接实现新的冲突修复算法前，先建设一个严格受限、可重复运行的离线参照工具。它以小规模联合状态 A* 给出精确参照结果，再用固定任务分配调用现有 `backend.app.dispatch.build_paths`，把可解性差异记录成可复现反例。

这是算法研究工具，不是新的业务 API，不进入前端，也不接管生产调度。

## 2. 平台后续实现顺序

现有可运行基线、综合场景和全量回归始终是每一阶段的前置门，不单独算一个新功能。在算法研究型平台方向下，后续按以下依赖顺序推进：

1. **小规模精确可解性参照与差分基准。** 先获得能区分数学无解、参照达到资源上限和当前规划器漏解的证据；这是本设计覆盖的第一项。
2. **有限窗口局部联合修复。** 只使用第一阶段确认的 `oracleSolvedPlannerMiss` 反例设计，限制参与机器人和修复时域，优先解除安全门重复停滞，不直接替换整个在线调度器。
3. **规模与拥堵性能研究。** 在可解性修复稳定后扩大固定种子、随机、瓶颈和在线压力覆盖，使用扩展状态数、候选数和 A* 调用数定位复杂度，再做缓存、剪枝或候选顺序优化。
4. **跨机器自适应窗口校准。** 规划工作量和墙钟波动得到充分记录后，才设计机器能力归一化或离线标定；当前同机 `60/40ms` 规则不直接推广成可移植阈值。
5. **复杂异构约束。** 在已有任务类型、载重和 `moveTicks` 基础上，再研究尺寸、转弯、能耗曲线、充电资源或通行权限；每类约束单独建模和验证，避免一次加入多个不可区分因素。
6. **中央—边缘协同。** 核心规划接口稳定后，将局部 A* 执行、中央任务/冲突协调、状态同步和失联降级拆成明确协议；在此之前不先制造分布式外壳。
7. **完整 CBS/MAPF 研究线。** 作为独立长期分支，与联合状态 A* 在重叠的小规模输入上交叉验证，再决定是作为对照、局部修复器还是替代候选，不能直接覆盖现有在线调度器。

持久化、多 Uvicorn worker 一致性、认证、外部监控和连续物理能耗属于产品化或仿真精细化方向。它们仍是已知缺口，但在当前算法研究主线中不先于上述 1—3 阶段。运行时库存状态已经实现；运行中改变货架物理位置属于另一个动态地图建模课题，也不混入第一阶段。

## 3. 方案比较

### 方案 A：联合状态 A*（采用）

把所有机器人在同一 tick 的位置组成一个联合状态，同时展开移动或等待动作。状态空间在本设计限定的最多 4 台机器人、最多 25 个可通行格内是有限的；开放集耗尽时可以在该运动模型下判定无解。实现只依赖 Python 标准库，语义直观，适合作为第一版精确参照。

代价是状态数随机器人数量快速增长，因此必须设置输入硬上限和显式扩展状态上限。达到上限只能报告 `limit`，不能报告 `unsolved`。

### 方案 B：先实现 CBS 参照

CBS 更接近常见 MAPF 研究路线，通常比朴素联合搜索更能扩展到较多机器人。但它需要正确实现低层约束搜索、高层冲突分裂、目标永久占用等细节；如果同时把它当参照和下一代生产算法，容易让同一实现错误同时污染“标准答案”和被测对象。

因此本阶段不采用。后续可以把 CBS 作为独立长期研究线，与联合状态 A* 在二者都能处理的小规模输入上交叉验证。

### 方案 C：SAT、ILP 或 CP-SAT 有界求解

这类方案适合在给定 makespan 上做可满足性判定，也有成熟研究基础，但会增加第三方求解器依赖、打包和版本复现成本。第一阶段不引入新依赖。

## 4. 目标与非目标

### 4.1 目标

- 对严格受限的小规模静态多机器人起点—终点问题返回 `solved`、`unsolved` 或 `limit`。
- `solved` 给出最小 makespan 和逐机器人路径；`unsolved` 只在完整有限状态图搜索耗尽后返回。
- 用固定分配调用现有 `build_paths`，不把任务分配差异混入路径规划比较。
- 自动分类“双方找到有效路径”“参照有解但当前规划器漏解”“参照无解且当前规划器未给出有效路径”“语义不一致”和“参照达到上限”。
- 通过确定性目录案例和固定种子生成案例寻找真实反例，并把完整输入、双方路径、失败和冲突写入报告。
- 复用现有 `run_isolated_process` 的 spawn、超时和清理语义；报告采用现有基准工具相同的 partial/final 和回滚保护约定。

### 4.2 非目标

- 不修改业务 API、Pydantic 请求/响应模型或前端。
- 不把参照求解器接入在线会话或生产 `run_dispatch`。
- 不处理任务分配、多个连续任务、释放时间、截止时间、服务时间、充电、故障、动态障碍或货架库存。
- 不声称支持任意规模，不声称达到完整 CBS/MAPF 的工程能力，也不把 `limit` 当作无解。
- 不把无侧向空间的一维交换场景记为现有规划器缺陷；只有 `oracleSolvedPlannerMiss` 才是下一阶段候选反例。

## 5. 精确问题模型

### 5.1 输入限制

新增离线数据类型 `SolvabilityAgent` 和 `SolvabilityCase`，不复用业务 `Scenario` 作为参照求解器输入。

硬限制如下：

- 地图宽、高各为 `1..5`，总格数不超过 `25`。
- 机器人数量为 `1..4`。
- 固定障碍、机器人起点和机器人目标均在地图内。
- 障碍不重复，且不与起点或目标重合。
- 机器人 ID、起点和目标分别唯一；目标可以等于某个机器人的起点，以覆盖交换类问题。
- 每台机器人只有一个必须访问一次的固定作业目标，单位速度，所有机器人从 T=0 同步开始。

非法案例在进入子进程前直接以 `ValueError` 拒绝。

### 5.2 运动和冲突语义

每个 tick，每台机器人可选择等待、上、右、下、左之一。动作必须保持在地图内且不能进入固定障碍。

联合动作必须同时满足：

- 下一 tick 不允许两台机器人位于同一格，防止顶点冲突；
- 不允许两台机器人互换上一 tick 的位置，防止反向边交换冲突；
- 首次到达自身目标后，该机器人的目标记为已经完成，之后允许继续移动到停车位置；当所有目标均已完成时搜索结束，输出路径结束后按现有 `detect_conflicts` 语义永久停留在各自最终位置。

搜索状态由联合位置和目标完成位掩码共同组成。因为环境和约束不随绝对时间变化，带有相同完成位掩码的同一联合位置不会因晚到而产生新机会；搜索只保留到达每个完整搜索状态的最小 `g`。

### 5.3 搜索和返回语义

精确参照函数为：

```text
solve_exact(case: SolvabilityCase, max_expanded_states: int) -> OracleResult
```

联合位置按 `case.agents` 的稳定顺序保存为 `tuple[Cell, ...]`，完成位掩码的第 i 位对应第 i 台机器人。A* 的代价 `g` 是已用 tick，启发式为所有尚未完成机器人的当前位置到自身目标曼哈顿距离最大值；已完成机器人贡献 0，因此该启发式不高估全部作业完成的最小 makespan。优先队列以 `(f, g, positions, completed_mask)` 排序，单机器人动作顺序固定为等待、上、右、下、左，使重复运行可重现。

返回规则：

- 初始状态已经访问全部目标时，返回 `solved`、`makespan = 0` 和每台机器人仅含起点的路径。
- 弹出的非过期状态完成位掩码已经覆盖全部机器人时，重建路径并返回 `solved`；每条路径必须包含对应作业目标，但允许最终停在目标以外的安全停车格。
- 需要展开下一个非目标状态、但 `expanded_state_count == max_expanded_states` 时返回 `limit`。
- 只有开放集耗尽时返回 `unsolved`。

`limit` 和 `unsolved` 均不返回伪造路径。

## 6. 现有规划器适配

每个 `SolvabilityCase` 转换成一个仅供离线比较的业务 `Scenario`：

- 每个 agent 对应一个 `Robot`，`moveTicks=1`，能力仅为 `inspection`，并提供足够但有限的电量；
- 每个 agent 对应一个 `serviceTime=0` 的单目标 `inspection` 任务；
- 每个任务通过 `Assignment(robotId=robot.id, tasks=[task])` 固定给对应机器人；
- 动态事件为空，运行时封锁和不可用机器人列表为空；
- 调用 `build_paths(scenario, scenario.robots, assignments, True, [], [])`；
- 使用现有 `detect_conflicts` 检查顶点冲突和反向边交换冲突。

生产侧只有在同时满足以下条件时才记为 `solved`：没有失败字符串、每台机器人都有路径、每条路径至少访问一次固定作业目标、`detect_conflicts` 返回空列表。访问全部目标但仍有冲突时记为 `conflicted`，其余情况记为 `failed`。生产 makespan 取各机器人首次到达自身目标 tick 的最大值，不把目标完成后的停车步计入任务完成时间。

本适配不调用任务分配器，因而差异只反映固定分配下的路径规划能力。

## 7. 案例来源

### 7.1 确定性目录

目录至少包含四个案例：

- 单机器人直达，参照应为 `solved`；
- 两机器人独立移动，参照应为 `solved`；
- 有侧向空间的两机器人换位，参照应为 `solved`；
- `3 × 1` 无侧向空间的两机器人换位，参照应为 `unsolved`。

目录只固定参照结果，不预先把当前规划器结果写成期望值，以免未来算法改进让诊断测试错误失败。

### 7.2 固定种子生成

生成器使用局部 `random.Random(seed)`，不修改全局随机状态。案例按 `(3×3, 2台)`、`(4×3, 2台)`、`(4×4, 3台)` 三种配置循环生成，障碍数从 `0..3` 中确定性采样。起点唯一、目标唯一，但目标允许占用其他机器人的起点。

生成器用独立静态 BFS 检查每台机器人忽略其他机器人时从起点可达目标，以排除显然由固定障碍造成的单机器人不可达案例。生成案例要求每台机器人起点不同于自己的目标，并拒绝重复的完整案例键。每个请求案例最多尝试 1,000 次；无法生成足量唯一案例时抛出 `RuntimeError`，不静默减少样本数。

默认固定种子为 `20260904`，默认生成 `64` 个案例，允许范围为 `0..512`。

## 8. 差分分类

完成运行使用以下精确分类值：

- `agreementSolved`：参照和当前规划器都给出有效无冲突路径；
- `oracleSolvedPlannerMiss`：参照有解，但当前规划器为 `failed` 或 `conflicted`；
- `oracleUnsolvedPlannerNoValidPlan`：参照无解，当前规划器未给出有效路径；
- `oracleUnsolvedPlannerSolved`：参照无解，但当前规划器被判为有效；该结果优先视为运动语义、适配或实现错误，不能直接当算法进步；
- `oracleLimit`：参照达到扩展状态上限，不能形成可解性结论。

子进程超时和异常使用独立运行结果 `timeout`、`error`，不强行填入上述分类。

只有 `oracleSolvedPlannerMiss` 案例进入报告顶层 `candidateCounterexampleCaseIds`，供下一阶段局部联合修复挑选回归输入。

## 9. 隔离、命令和报告

新增根命令：

```powershell
npm run benchmark:solvability -- --sample-count 64 --seed 20260904 --repetitions 1 --max-expanded-states 100000 --timeout-seconds 5
```

默认输出根目录为 `output/solvability-differential`，每次运行创建 UTC 时间戳子目录。每个案例的每次重复都在独立 spawn 子进程中运行，直接复用 `backend.benchmarks.process_isolation.run_isolated_process`。基础设施无法确认子进程停止时继续抛出 `BenchmarkInfrastructureError`，不能降级成普通算法超时。

报告 `schemaVersion=1`，最终文件为：

- `results.json`：配置、完整案例输入、逐次结果、逐案例汇总和候选反例 ID；
- `runs.csv`：逐次扁平记录，路径、失败和冲突字段编码为紧凑 JSON；
- `case-summaries.csv`：逐案例分类稳定性和用时汇总。

每个案例结束后原子替换 `results.partial.json`。最终三文件按现有基准报告相同的临时文件、备份、发布和回滚顺序处理；成功后删除 partial。任何超时、`error` 和 `oracleLimit` 都保留在最终报告中。

发现 `oracleSolvedPlannerMiss` 是工具的正常研究产出，不使 CLI 返回失败。参数无效、目录创建失败、子进程基础设施失败或报告发布失败返回非零。

## 10. 测试与验收

### 10.1 参照求解器

- 单机器人最短路径、初始已达目标和必要等待场景给出准确 makespan。
- 有侧向空间换位为 `solved`，`3 × 1` 无侧向换位为 `unsolved`。
- 所有 `solved` 路径逐 tick 无顶点冲突、无反向边交换冲突，每条路径都访问对应目标，最终联合位置可以持续安全占用。
- 极低扩展上限得到 `limit`，不会得到 `unsolved`。
- 相同输入重复执行得到相同 outcome、makespan、扩展状态数和路径。

### 10.2 差分适配

- 生产适配使用固定 `Assignment`，不调用任务分配函数。
- 简单案例分类为 `agreementSolved`。
- 通过替身返回失败或冲突路径时分类为 `oracleSolvedPlannerMiss`。
- 无旁路换位不会被标记为 `oracleSolvedPlannerMiss`。
- `oracleUnsolvedPlannerSolved` 和 `oracleLimit` 保留独立语义。

### 10.3 运行与报告

- 子进程完成、超时、异常和基础设施异常沿用现有清理保证。
- 批量执行不中途删除超时或异常记录，回调接收累计副本。
- JSON 为 UTF-8，CSV 为带 BOM 的 UTF-8；三份最终文件可以互相重算记录数量和分类计数。
- 最终发布失败时恢复旧三文件和 partial，不留下未解释的半成品。
- 参数在创建输出目录前验证；相同秒内的目录名使用递增后缀。

### 10.4 项目回归

聚焦测试通过后执行当前完整检查：

```powershell
.\.venv\Scripts\python.exe -m pytest backend/tests/test_solvability_oracle.py backend/tests/test_solvability_differential.py
npm run check
```

完整检查必须继续覆盖前端构建、前端测试和全部后端测试。历史 `219/219` 与 `798 passed, 19 skipped` 只作为 2026-08-30 基线，不替代实现后的新结果。

## 11. 后续连接点

本工具产出的 `oracleSolvedPlannerMiss` 案例是第二阶段“有限窗口、少量冲突机器人局部联合修复”的唯一首批输入来源。局部修复必须先把至少一个真实反例转成固定回归，再设计生产接入点；不得依据人工想象的困难场景直接改写 `build_paths`。

当联合状态 A* 在 4 台机器人或 25 格限制内经常返回 `limit` 时，再单独评估 CBS 参照。中央—边缘协同只在核心规划和比较证据稳定后设计，避免先制造分布式接口而没有明确算法边界。
