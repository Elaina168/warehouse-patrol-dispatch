# 在线会话执行安全门设计

## 1. 目标

为开启避碰的在线调度会话增加独立的执行前安全门，保证已经写入会话路径历史的 tick 不出现以下两类碰撞：

- 顶点冲突：两台机器人在同一 tick 位于同一单元格。
- 反向边交换冲突：两台机器人在同一 tick 沿同一条边反向交换位置。

当前优先级时空 A* 会尝试若干机器人规划顺序，并在存在零失败、零冲突、零超期候选时提前结束；如果没有这样的候选，仍会返回评分最好的带冲突候选。安全门不替代现有规划器，而是在路径真正进入在线会话历史前阻止不安全动作。

本功能只保证“没有安全动作就不执行”，不保证任意场景都能找到无冲突路线。

## 2. 已确认范围

### 2.1 生效范围

- `DispatchOptions.avoidConflicts = true` 的在线会话启用安全门。
- `avoidConflicts = false` 的基线对比保持现状，允许展示和执行预测冲突。
- `POST /api/dispatch` 及六个实验接口继续返回规划预测及其冲突，不模拟在线执行拦截。
- 运行时活动封锁继续作为所有策略下的硬约束，机器人不得进入活动封锁格。

### 2.2 不在范围内

- 不引入 CBS、ECBS 或完整 MAPF 求解器。
- 不承诺全规划时域一定存在零冲突方案。
- 不增加连续若干次拦截后自动放弃任务的策略。
- 不自动解除任务锁，不改变抢占评分、充电策略或机器人资格规则。
- 不新增实验面板、展示页面或独立安全面板。
- 不对 `backend/app/dispatch.py` 或 `backend/app/sessions.py` 做无关重构。

## 3. 对外数据契约

复用现有 `Conflict` 结构，在 `SessionResult` 中增加必有但可空字段：

```python
safetyIntervention: Conflict | None = None
```

前端对应类型为：

```ts
safetyIntervention: Conflict | null;
```

没有拦截时返回 `null`。发生拦截时返回被安全门阻止的首个冲突，时间使用绝对会话时间：

```json
{
  "time": 7,
  "type": "vertex",
  "robots": ["R1", "R2"],
  "cell": [3, 2]
}
```

`DispatchResult` 不增加安全字段。离线调用方仍通过 `avoidConflicts` 与 `conflicts` 判断规划预测；只有在线 `SessionResult` 表达是否真正发生执行拦截。

## 4. 会话状态

`DispatchSession` 增加：

```python
last_safety_intervention: Conflict | None = None
```

状态规则：

- 创建会话和重置会话时为 `None`。
- 普通读取、任务追加、封锁、故障和恢复操作不清除最近一次拦截，便于操作者检查原因。
- 下一次实际 tick 尝试开始时清除旧值；如果本次再次拦截，写入新的冲突；如果本次安全推进，响应恢复为 `null`。
- 事件日志保留历史拦截记录，结构化字段只表示最近一次 tick 尝试的结果。

## 5. 后端组件边界

### 5.1 首个危险 tick 选择

在 `backend/app/sessions.py` 增加纯函数，输入当前 `DispatchResult`、当前会话时间和请求目标时间，返回区间 `(currentTime, targetTime]` 内时间最早的冲突：

```python
def _first_execution_conflict(
    result: DispatchResult,
    current_time: int,
    target_time: int,
) -> Conflict | None
```

排序规则固定为：

1. `time` 较早者优先。
2. 同 tick 时 `vertex` 先于 `edge`。
3. 再按 `robots` 和 `cell` 的现有值排序，保证测试和日志确定性。

该函数只选择已有规划冲突，不重新实现冲突检测。

### 5.2 安全等待写入

增加一个只负责写入安全等待 tick 的内部函数：

```python
def _apply_safety_hold(
    session: DispatchSession,
    result: DispatchResult,
    conflict: Conflict,
) -> None
```

它执行以下原子步骤：

1. 将每台机器人的上一 tick 位置追加到 `robot_path_history`，即全车原地等待一个 tick。
2. 将 `robot_positions` 同步到等待后的位置。
3. 不增加 `robot_travelled_distance`，不扣减电量。
4. 使用实际历史路径同步任务路点、货物位置、作业时间和完成状态，禁止使用未执行的冲突路径产生取货或目标完成。
5. 将会话时间推进到 `conflict.time`。
6. 写入 `last_safety_intervention`。
7. 记录事件：`T=<time> 执行安全门拦截 <type> 冲突：<robots>`。
8. 使缓存计划失效，确保下一次推进从实际位置重新规划。

为避免复制现有库存、任务进度和完成逻辑，可把 `_advance_session` 中“根据已经落地的路径历史同步业务状态”的代码提取为单一内部辅助函数。只做支撑安全门所需的局部提取，不改变其业务语义。

### 5.3 `_advance_session` 控制流

保留当前动态事件、滚动窗口和任务完成触发点的绝对时间语义，并把安全冲突作为新的时间边界：

1. 当 `avoidConflicts = false` 时，完全沿用现有推进路径。
2. 当 `avoidConflicts = true` 时，在本次请求区间内查找首个规划冲突。
3. 如果没有冲突，正常推进到 `targetTime`。
4. 如果冲突发生在请求区间中：
   - 先正常推进到 `conflict.time - 1`；
   - 在 `conflict.time` 写入全车安全等待；
   - 返回，不继续推进到原请求的更远目标时间。
5. 如果场景动态事件、滚动窗口触发或任务完成与安全冲突位于同一 tick，先落地安全等待和实际任务进度，再激活该 tick 的动态/窗口状态，最后使计划失效。所有事件仍使用同一个绝对 tick。

因此，请求从 `T=0` 跳到 `T=20`、首个危险 tick 为 `T=7` 时，响应 `currentTime` 必须是 `7`，而不是 `20`。

## 6. 任务、库存、电量与时间语义

- 安全等待是真实经过的一个业务 tick，截止时间继续推进。
- 所有机器人等待，因此本 tick 移动距离为零，电量不下降。
- 未到达的任务目标、取货点和放货点不得因原预测路径而完成。
- 已经在作业格开始服务的机器人保持原位，因此其作业等待可以继续累计。
- 只有依据实际 `robot_path_history` 满足全部路点和作业时间的任务才能完成。
- 安全拦截不直接将任务改为永久失败，也不新增恢复动作枚举。
- 重新规划仍找不到安全路线时，后续 tick 可以再次拦截；系统保持安全等待，不降级执行冲突路径。

## 7. 前端行为

前端只消费结构化字段，不解析中文事件文本：

- `applySessionPayload` 收到非空 `safetyIntervention` 时调用 `setPlaying(false)`，自动暂停播放。
- 顶部现有状态区域显示“安全门已拦截冲突”，并显示绝对 tick、冲突类型和机器人 ID。
- 地图复用现有冲突单元及冲突机器人样式，额外把 `safetyIntervention` 纳入当前高亮来源。
- 不新增面板、弹窗或新的人工确认步骤。
- 用户再次点击播放时发起下一 tick；后端从实际等待位置重新规划。安全推进成功后，`safetyIntervention` 返回 `null`，提示消失。
- 现有会话请求代际与串行协调器继续负责丢弃重置前的陈旧响应，安全字段不绕过该机制。

## 8. 错误处理与可观测性

- 安全门是成功的会话状态转换，不返回 HTTP 错误；响应仍为 `200`。
- `currentTime` 小于请求目标时间表示请求在首个危险 tick 被提前终止，前端必须以响应时间为权威。
- 每次实际拦截写入一条事件日志；一个请求只处理首个冲突，因此不会在单次大跨度请求中写入大量重复事件。
- 日志继续受 `MAX_SESSION_EVENT_NOTES` 限制。
- `metricsHistory` 在拦截 tick 记录快照；`activeConflictCount` 必须为 `0`，因为冲突动作没有实际执行。
- 规划结果仍可包含未来预测冲突，但 `safetyIntervention` 与事件日志明确区分“预测冲突”和“已拦截执行冲突”。

## 9. 测试设计

### 9.1 后端算法和会话测试

新增确定性测试：

1. 强制能力分工的三格单通道场景复现当前顶点冲突；开启避碰后推进到危险 tick，两台机器人不能落在同一格。
2. 构造反向边交换路径，验证两台机器人不会交换位置。
3. 从较早 tick 大跨度请求到较晚 tick，验证响应停在首个危险 tick。
4. 验证所有 `robot_path_history` 已执行 tick 都不存在顶点或反向边冲突。
5. 验证安全等待不增加距离、不扣电、不误触发取货、放货或目标完成。
6. 验证已开始的原地作业时间在安全等待 tick 正常累计。
7. 验证重复无解时持续安全等待，不执行冲突路径。
8. 验证 `avoidConflicts = false` 的基线对比行为不变。
9. 验证重置清除 `safetyIntervention`，普通读取和运行时更新保留最近一次拦截，下一次安全 tick 清除它。
10. 验证场景动态事件或滚动窗口触发与拦截同 tick 时，事件时间与状态均保持绝对会话时间。

### 9.2 API 契约测试

- 后端 `SessionResult.safetyIntervention` 与前端 `SessionResult.safetyIntervention` 字段对齐。
- 字段在 JSON 中始终存在，值为 `null` 或现有 `Conflict` 结构。
- 普通读取和运行时更新保留最近一次拦截，下一次安全 tick 返回 `null`，字段生命周期与会话状态规则一致。
- OpenAPI 会话响应模型继续使用 `SessionResult`。

### 9.3 前端测试

- 非空 `safetyIntervention` 自动暂停播放。
- 状态文案使用结构化冲突字段。
- 地图复用现有样式高亮冲突单元和机器人。
- `null` 时不显示安全提示。
- 陈旧会话响应不能重新显示已经被重置清除的安全拦截。

### 9.4 回归验证

必须保持以下现有验收通过：

- `integrated-demo` 六任务在 `T=700` 前完成，冲突、失败、超期和充电访问均为零。
- 固定种子、在线压力、充电、库存、机器人能力与恢复测试通过。
- 前端生产构建和全部前端测试通过。
- 全部后端测试通过。
- 最终运行 `npm run check`。

## 10. 完成标准

满足以下条件才可以声称执行安全门完成：

- 开启避碰的在线会话中，任何已经写入路径历史的 tick 都没有顶点或反向边交换冲突。
- 规划器返回带冲突候选时，会话在首个危险 tick 安全等待并提前结束本次推进。
- 前端根据结构化字段暂停并解释拦截，不依赖中文日志解析。
- 任务、库存、电量、作业时间、动态事件和滚动窗口保持既有绝对时间语义。
- 基线对比仍能展示冲突，离线实验接口行为不变。
- 完整项目检查通过。
