# 项目需求清理与指标语义统一设计

日期：2026-07-14

## 1. 背景与目标

当前核心在线调度平台已经形成闭环，但主界面、实验接口、指标字段和项目文档之间存在历史遗留口径：默认综合场景没有预设动态事件，主界面仍显示动态事件开关；实验面板已从主界面删除，但前端仍保留相关辅助代码；运行时任务统一走同一个追加接口，但响应仍区分已经失效的手工/自动任务计数；固定种子和在线压力接口都把不同含义的比例称为完成率；项目总完成度与竞赛材料、3D 等模块状态不一致。

本次工作目标是统一已经确认的需求语义，删除无效前端入口和遗留代码，修正后端实验指标与会话契约，补齐文档，并保护已经人工确认的综合演示基线。

## 2. 范围

本次包含：

- 删除主界面的动态事件开关和状态文字。
- 保留后端场景动态事件机制，并在主界面会话中固定启用。
- 删除旧实验面板遗留的前端代码、样式、类型、客户端函数和测试。
- 保留全部后端实验接口和后端回归。
- 统一任务优先级为 `0` 到 `5`。
- 统一运行时追加任务计数，删除失真的自动流计数。
- 区分任务分配率、在线覆盖率和实际完成率。
- 明确当前避碰硬标准、算法质量标准和未实现的全时域目标。
- 修正主演示充电能力的表述。
- 补充固定种子压力和在线压力接口文档。
- 用模块状态替代缺少统一计算依据的完成百分比。
- 纳入当前工作区已经完成的固定 demo 恢复链路、截止时间和 UTF-8 测试修复。

本次不包含：

- 删除后端动态事件机制。
- 恢复独立实验面板或创建新实验页面。
- 为手工任务和自动生成任务增加来源字段或独立接口。
- 修改综合场景电量以强制展示充电。
- 实现完整 CBS/MAPF。
- 实现全时域零冲突安全门。
- 重做真实仓库地图、机器人任务类型能力或 3D 展示。

## 3. 动态事件机制与主界面

后端继续保留 `DynamicEvent`、`DispatchOptions.includeDynamic`、动态重规划实验和相关测试。固定种子、自定义导入场景和后端实验仍可使用预设动态任务、动态封锁和动态机器人故障。

主界面删除：

- `includeDynamic` 可编辑状态。
- “启用突发任务与重规划”复选框。
- 顶部“动态事件/静态流程”状态文字。
- 仅用于该状态文字的格式化函数和测试。

主界面创建会话时固定发送 `includeDynamic: true`。默认 `integrated-demo` 的动态任务、动态封锁和动态故障列表为空，因此不会出现额外触发；导入含动态配置的场景时按其配置自动触发，主界面不提供临时关闭入口。

手工任务、定时生成任务、运行时封锁和机器人故障使用运行时 API，不依赖场景动态事件开关，相关功能保持不变。

## 4. 实验面板遗留清理

主界面和 `docs/experiments.md` 是当前产品入口事实来源：主界面不保留独立实验面板。

删除仅服务旧实验面板的前端内容：

- `main.tsx` 中实验面板汇总行、图表、差值卡片、自动结论、CSV、空状态和状态标签辅助逻辑。
- `styles.css` 中实验面板专用样式。
- `sessionApi.ts` 中后端实验接口客户端函数。
- `types.ts` 中仅供旧实验面板客户端使用的实验请求和响应类型。
- 对上述前端遗留逻辑的单元测试。

后端的避碰、动态重规划、滚动窗口、规模、固定种子压力和在线压力接口全部保留，并继续由 pytest 直接验证。README 和实验文档明确这些接口用于自动化回归、性能证据和报告取数，不属于主演示界面。

## 5. 主演示充电口径

系统已经实现离散网格电量消耗、充电路线、充电等待、充电期间不可抢占以及充电路线封锁恢复。

`integrated-demo` 保留充电地块、电池容量和当前电量展示，但默认流程不要求实际产生 `chargingVisits`，不修改机器人初始电量来强制充电。文档改为：完整充电闭环通过低电量测试场景和自动化回归验证。

## 6. 优先级语义

统一使用 `0` 到 `5`，数值越大越优先：

| 数值 | 语义 |
| ---: | --- |
| 0 | 普通后台任务 |
| 1 | 低优先级 |
| 2 | 普通优先级 |
| 3 | 高优先级 |
| 4 | 紧急 |
| 5 | 最高/突发 |

具体规则：

- 后端任务模型将优先级正式限制为 `0` 到 `5`，超出范围的 API 输入和导入场景必须被拒绝。
- 手工任务输入允许 `0` 到 `5`。
- 手工突发任务最低为 `4`。
- 随机巡检和配送任务使用 `0` 到 `3`。
- 随机突发任务使用 `4` 到 `5`。
- 新任务优先级严格大于已锁定任务时才进入抢占比较。
- 同优先级任务不抢占。
- 删除所有以 `-1` 表示普通任务的计划和说明。

## 7. 运行时追加任务计数

手工任务和前端定时生成任务继续统一调用 `POST /api/sessions/{session_id}/tasks`。不恢复旧的 `/stream-task`，不增加来源字段。

后端不再声称能够区分手工和自动来源：

- 会话内部 `manual_task_count` 改为统一的运行时追加任务计数。
- API 字段 `manualTaskCount` 改为 `runtimeTaskCount`。
- 删除 API 字段 `streamTaskCount`。
- 会话详情、会话摘要、重置逻辑、容量测试、前端类型、API 契约和文档同步修改。

所有通过统一任务追加接口成功加入的任务都使 `runtimeTaskCount` 增加一。

## 8. 固定种子压力指标

固定种子压力接口是一次性规划实验，不推进在线执行。原 `completionRatePercent` 实际计算已分配任务数除以任务总数，因此改为 `assignmentRatePercent`。

接口继续返回：

- `taskCount`
- `assignedTaskCount`
- `assignmentRatePercent`
- 稳定场景数量和稳定率
- 冲突、截止超期和失败
- 总路径、平均每任务路径和 makespan
- 平均/最大规划耗时
- 规划时间预算及通过率

稳定条件保持为：全部任务已分配、冲突为 0、截止超期为 0、失败为 0。

## 9. 在线压力指标

在线压力实验继续使用统一任务追加接口，在固定时间加入运行时任务，并经历动态事件、封锁、故障、恢复和时间推进。

实验 case 增加或调整：

- `releasedTaskCount`：实验结束时有效释放时间不晚于当前时间的任务数。
- `runtimeTaskCount`：通过统一运行时任务接口加入的任务数。
- `coverageRatePercent`：替代原来含义错误的 `completionRatePercent`。
- `actualCompletionRatePercent`：已完成任务数除以已释放任务数；没有已释放任务时为 0。
- 删除 `manualTaskCount` 和 `streamTaskCount`。

实验 summary 对应使用：

- `totalReleasedTaskCount`
- `totalRuntimeTaskCount`
- `coverageRatePercent`
- `actualCompletionRatePercent`
- 删除 `totalManualTaskCount` 和 `totalStreamTaskCount`

覆盖任务的现有判定保持为任务状态不是 `unassigned`。覆盖率用于判断任务是否丢失或进入当前无法调度状态，不代表完成。

在线稳定条件保持为：所有任务被覆盖、冲突为 0、截止超期为 0、失败为 0。固定时间结束时不要求全部任务完成。

## 10. 避碰验收标准

### 10.1 当前硬标准

在线实际执行的任一 tick 不允许出现：

- 两台机器人占用同一单元的顶点冲突。
- 两台机器人在同一 tick 迎面交换位置的边冲突。

运行时任务、封锁、故障和恢复后仍应满足当前活动冲突为 0。发现下一执行步不安全时必须等待、绕行或重规划。

### 10.2 当前算法质量标准

- 固定种子压力场景要求整条预测路径冲突为 0。
- 综合主演示要求开启避碰后的预测冲突少于关闭避碰。
- 综合主演示允许暂时存在少量远期预测冲突，但必须在其执行时间到达前消解。
- 文档不得把“预测冲突降低”表述为“已经实现全时域零冲突”。

### 10.3 未实现的后续目标

每次规划返回的整条未来路径严格零冲突，并由执行前安全门阻止任何不安全动作。该能力当前没有实现，属于后续独立算法升级，不计入当前完成项。
