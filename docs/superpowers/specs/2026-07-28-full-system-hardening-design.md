# 全系统审查问题加固设计

日期：2026-07-28
状态：已确认总体方向，待用户审阅书面规格
目标分支：`codex/full-system-hardening`

## 1. 背景与目标

当前 `main` 在提交 `de02ffb5d305a05c2a6a762c48c7ef2a70520de9` 上通过了前端构建、105 项前端测试和 523 项后端测试，但全仓库审查仍复现出执行安全、会话事务、前端在线操作、开发脚本和离线工具链问题。

本批次只修复已确认的问题，不新增业务功能，不重写任务分配或 MAPF 算法，不增加展示型面板。完成后的系统必须满足：

1. 机器人不会在电量耗尽后继续执行移动。
2. 被拒绝的运行时请求不会部分推进或修改会话。
3. 会话不能从重叠机器人起点启动。
4. T=0 完成任务走统一的完成、库存和重规划流程。
5. 外部输入不能通过持续时间或实验批次制造无界规划工作。
6. 在线操作不会因 tick 排队而携带过期时间。
7. 历史回放不再伪装成完整的历史状态快照。
8. 开发脚本只停止本项目明确记录的进程。
9. 检查脚本、benchmark 报告和依赖环境具备可信的失败传播与复现能力。

## 2. 实施分组

修复在同一功能分支中按四个连续批次完成，每批独立测试和审查：

1. 后端执行安全与会话一致性。
2. 输入与资源边界。
3. 前端在线操作与可信回放。
4. 开发脚本、benchmark 和依赖工具链。

四批可以形成多个小提交，但合并前必须作为一个整体完成全量审查。任何批次失败不得通过弱化断言、放宽安全语义或删除已有覆盖解决。

## 3. 后端执行安全与会话一致性

### 3.1 实际路径电量校验

现有静态距离仍可用于任务分配的快速可行性判断，但不能作为最终执行电量的权威依据。

规划器生成每段 `astar_timed` 路径后，必须按实际位置变化次数计算移动耗电；等待 tick 不耗电。路径只有在以下条件满足时才可作为可执行候选：

- 每次移动前剩余电量大于 0。
- 到达已计划的充电站并完成充电后，电量恢复到 `batteryCapacity`。
- 任何时序绕行增加的移动量都计入消耗。

若避碰路线使电量不足，当前候选应安全失败并允许其他规划顺序继续尝试；所有候选都不足时返回结构化任务失败，不得返回机器人在零电量下继续移动的路径。

在线执行层增加不变量保护：即使缓存或未来代码回归产生非法路径，也不得把零电量移动写入机器人历史。该情况应保持原位、使计划失效并记录可解释事件，而不是把电量钳制为 0 后继续移动。

### 3.2 机器人起点互斥

场景验证新增机器人起点唯一性检查。两个不同机器人 ID 使用同一 `start` 时，直接调度和在线会话创建都返回 422。

该校验发生在规划和会话发布前。执行安全门继续只负责未来顶点冲突和反向边冲突，不承担修复非法 T=0 初始状态的职责。

### 3.3 未来运行时封锁的事务语义

未来封锁请求必须遵循“预演后提交”：

1. 复制会话运行时权威状态到隔离预演对象；锁、外部 observer 和注册表身份不复制。
2. 在预演对象上推进到请求时间，包括任务完成、滚动窗口、动态事件和重规划。
3. 在预演后的真实目标时刻检查机器人占用和封锁合法性。
4. 预演失败或请求应返回 409/422 时，丢弃预演对象，原会话的时间、路径历史、任务、库存、指标、事件和缓存均保持不变。
5. 预演通过后，再对真实会话执行同样推进并提交封锁。

预演不得调用校准 observer、写入全局会话注册表或改变访问时间。该 helper 只服务需要未来状态验证的运行时操作，不重构全部会话存储。

### 3.4 统一任务完成转换

普通 tick 完成和 T=0 同步完成使用同一个内部完成转换，负责：

- 写入 `completed_task_ids` 和 `task_completion_times`。
- 清除任务载荷位置、偏好和任务锁。
- 对出库取货与入库完成应用权威库存转换。
- 记录且只记录一次任务/库存事件。
- 使包含已完成任务的缓存计划失效。

会话创建或重规划在 T=0 发现即时完成后，应继续进行有界重规划，直到：

- 没有新的 T=0 即时完成任务；或
- 所有任务已处理。

循环次数最多为当前任务总数，防止错误输入或回归造成无限循环。容量窗口中排在即时完成任务后的已释放任务必须在同一创建响应中进入有效计划，不能永久 `pending`。

## 4. 输入与资源边界

### 4.1 持续时间和路径预算

复用现有在线会话最大时间 `10_000` 作为统一规划时域：

- `Task.serviceTime`：`0..10_000`。
- `Scenario.chargeTime`：`1..10_000`。
- 单机器人规划路径：最多 `10_000` tick，即最多 `10_001` 个位置节点。

schema 超限输入直接返回 422。多个合法任务累计超过路径预算时，规划器在追加前检查预算并安全返回“规划路径超过最大时域 10000 tick”的永久失败，恢复动作使用现有 `fixTaskDefinition`，不得先物化超大路径。

前端人工任务的作业时间输入使用相同最大值并在构造任务时做整数裁剪；后端仍是最终校验权威。

### 4.2 实验批量上限

新增统一实验批次上限 `32`：

- `ReplanWindowExperimentRequest.windows`：长度 `1..32`，不允许重复窗口。
- `ScaleExperimentRequest.cases`：长度 `1..32`。

空批次、重复窗口和超限批次在进入任何 `run_dispatch` 前返回 422。现有标准、扩展 seeded 和 online pressure 固定案例接口保持不变。

## 5. 前端在线操作与可信回放

### 5.1 tick 与 mutation 串行边界

`tickInFlight=true` 时禁止产生新的在线 mutation：

- 地图封锁与解除封锁。
- 机器人故障与恢复。
- 任务恢复按钮。
- 人工任务提交。
- 自动任务生成。

按钮和地图交互必须有可见 disabled 状态，事件 handler 也做保护，防止仅靠 DOM disabled。请求协调器仍保持同会话串行执行和 generation 失效保护。

运行时 block/fail/restore 请求继续传递精确 `currentTime`；禁止通过删除该字段掩盖竞态。用户在 tick 完成后重新操作时，使用更新后的权威会话时间。

### 5.2 HTTP 业务错误与连接错误分离

前端 API 错误对象保留 HTTP status。

- 4xx：后端仍为 `online`，保留最后一个有效会话结果，mutation 不改变播放状态，页面显示具体业务错误。
- tick 的 4xx：后端仍为 `online`，暂停播放并显示错误，因为目标时间没有推进。
- 5xx、网络失败或无法解析响应：标记后端异常/离线，暂停播放并进入错误状态。

业务错误需要独立的可见操作错误区域或状态文本；不能依赖仅在 `result=null` 时渲染的占位组件。下一次成功操作、重置或场景切换清除该错误。

### 5.3 可信路径回放

本批次不新增后端逐 tick 完整状态快照。

当 `displayTime < session.currentTime` 时，前端进入明确的“历史路径回放”模式：

- 继续显示路径位置、截至该 tick 的事件和指标历史。
- 不使用最新 `taskStates` 伪造过去任务状态。
- 不显示最新 `extraBlocked`、`unavailableRobotIds` 和库存状态作为过去覆盖层。
- 任务队列和库存区域显示“历史回放仅提供路径、事件和指标；返回最新 tick 查看实时状态”。
- 历史模式禁止运行时封锁、故障、恢复和任务提交。

回到 `session.currentTime` 后恢复完整实时状态与操作能力。界面不得声称该模式提供完整历史任务或库存快照。

### 5.4 会话创建清理

场景或策略切换不再通过丢弃已完成的 create 响应制造孤儿：

- create 请求开始后允许读取成功响应。
- generation 已失效时，使用响应中的 `sessionId` 立即调用 DELETE，而不是应用到 UI。
- effect cleanup 同时使 generation 失效。
- 当前活动会话仍按既有逻辑在替换或卸载时删除。

网络在服务器创建成功后、客户端取得响应前彻底中断时仍可能依赖后端 TTL/LRU；本批次不引入幂等请求 ID 或持久化事务。

### 5.5 导入验证契约对齐

前端导入器必须接受后端允许的 `null` 时间字段，不得把未来 `dynamic.blockedCells` 当成立即固定障碍。

本地结构检查补齐：

- `priority` 为 `0..5` 整数。
- `releaseTime`、`deadline`、`serviceTime` 为 `null`、缺省或对应范围内整数。
- 地图轴长不超过 64，总单元不超过 1024。
- 机器人不超过 32，初始与动态任务合计不超过 128，单任务目标不超过 64。
- `serviceTime`、`chargeTime` 使用第 4.1 节上限。
- 机器人起点不得重复。

定义级可达性和库存规则仍由后端验证；前端错误只做快速反馈。API 契约测试增加这些精确常量与 nullable 规则，防止再次漂移。

## 6. 开发脚本、benchmark 与依赖

### 6.1 项目进程清单

新增被忽略的 `.runtime/` 目录和开发进程清单，例如 `.runtime/dev-processes.json`。清单记录启动脚本创建的顶层 PID、进程启动时间和角色。

`start-dev.ps1`：

- 启动成功后原子更新清单。
- 启动前只清理清单中仍匹配 PID 与启动时间的旧项目进程。
- 未记录进程占用端口时，不强杀；兼容后端可复用，不兼容服务或被占用的前端端口给出明确错误。

`stop-dev.ps1`：

- 只停止清单中身份仍匹配的进程树。
- PID 已复用或身份不匹配时跳过并报告。
- 不再按 `5174/8011/8000/8001` 端口扫描并强杀任意进程。
- 清理成功后删除清单；停止失败时保留未确认条目。

### 6.2 完整检查脚本

`scripts/test-all.ps1` 调用与根 `npm run check` 相同的三段检查，并在任一原生命令非零时立即以非零退出：

1. 前端生产构建。
2. 前端测试。
3. 后端测试。

脚本不得依赖 `$ErrorActionPreference` 隐式传播原生命令退出码。增加脚本级回归，证明第一、第二或第三段失败都不会假成功。

### 6.3 benchmark 取消清理

隔离运行器的资源清理放入覆盖 `BaseException` 的 `finally` 路径：

- 正常完成、普通异常、超时、`KeyboardInterrupt` 和 `SystemExit` 都关闭 Pipe。
- 已启动子进程都执行有界 join；需要时 terminate → bounded join → kill → bounded join。
- 清理成功后重新抛出原始取消异常。
- 无法确认子进程停止时仍升级为 `BenchmarkInfrastructureError`。

### 6.4 最终报告事务发布

算法 benchmark 的 `results.json`、`runs.csv` 和 `case-summaries.csv` 先写入同目录 staging 文件并全部验证成功，再替换最终 bundle。

若任一步失败：

- 已存在的旧完整 bundle 保持不变；或
- 若此前没有旧 bundle，则不暴露任何新“最终文件”。

`results.partial.json` 只在完整最终 bundle 发布后删除。复用 adaptive reporting 已有的 staging/rollback 语义，避免形成两套不同保证。

### 6.5 测试中的墙钟门槛

日常 pytest 移除对真实 `replanTimeMs < 1000/2000` 的硬失败断言。保留：

- 零冲突、零失败、分配率和案例结构断言。
- `planningTimeBudgetMs` 字段定义断言。
- 确定性的规划诊断工作量断言。

真实墙钟继续只由离线 benchmark 重复运行后人工比较。

### 6.6 前后端依赖

- 前端通过 lockfile/override 将 PostCSS 固定到已修复的 `8.5.18` 或更高兼容补丁版本；`npm audit` 不得再报告 `GHSA-r28c-9q8g-f849`。
- 保留 `backend/requirements.txt` 作为直接依赖清单。
- 新增 `backend/requirements.lock.txt`，记录当前验证环境的完整传递依赖精确版本。
- 环境文档使用 lock 文件安装可复现环境，并说明更新直接依赖后需要重新生成和验证 lock。
- `pip check` 必须通过。

本批次不引入新的包管理器，不猜测或声称未经过审计的 Python CVE。

## 7. 测试策略

每个生产行为按 RED → GREEN 实施。至少增加以下回归：

1. 时序绕行超过电量时不产生零电量移动路径；在线历史也无零电量移动。
2. 未来封锁在中途重规划后返回 409 时，会话所有权威字段保持不变。
3. 重复机器人起点在直接调度和会话创建前被拒绝。
4. T=0 即时完成后下一任务进入计划；入库/出库库存副作用正确且事件不重复。
5. 时长字段和累计路径预算边界的等于上限、超过上限测试。
6. 实验空批次、重复窗口、32 与 33 个元素边界测试。
7. tick 期间所有 mutation 入口禁用且 handler 不发请求。
8. 4xx、5xx、网络错误和成功恢复的前端状态决策测试。
9. 历史路径回放不读取最新任务、库存、封锁和故障覆盖层。
10. 失效 create 成功响应触发 DELETE。
11. 导入 nullable、未来动态封锁、规模和整数边界测试。
12. stop 脚本仅处理匹配清单进程，未知端口进程不被调用 `taskkill`。
13. test-all 三阶段调用和退出码传播测试。
14. benchmark `KeyboardInterrupt`/`SystemExit` 清理和无残留 worker 测试。
15. 最终报告第二、第三文件失败时的 rollback 测试。
16. 依赖 lock 一致性、`npm audit` 和 `pip check`。

## 9. 验收标准

全部满足后才可称为完成：

1. 审查报告中的 18 项问题均有修复或明确由同一修复消除。
2. 所有新增回归先观察到预期失败，再由最小实现转绿。
3. 已执行历史不存在零电量移动、T=0 重叠或被拒绝请求的部分提交。
4. 历史模式不显示无法证明属于该 tick 的当前状态。
5. 启停脚本不会根据端口终止未登记进程。
6. 完整检查、依赖审计、`pip check` 和差异检查通过。
7. 未跟踪的 `.superpowers/`、`output/` 保持不提交；`.runtime/` 被忽略且不提交运行产物。
8. 最终全分支代码审查无 Critical/Important 未解决问题。
