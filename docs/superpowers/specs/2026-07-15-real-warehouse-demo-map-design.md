# 真实仓库综合演示地图设计

日期：2026-07-15

## 1. 背景与目标

当前唯一前端场景 `integrated-demo` 使用 `14 × 10` 抽象网格和多列障碍，能够覆盖在线调度功能，但仓库业务分区、货架组、通道宽度和巡检结构不够直观。本次工作直接升级这一共享基线，不新增第二张主演示地图。

目标是把场景改造成更接近真实仓库的竞赛地图，同时继续保护现有在线调度、取送、巡检、优先级、延迟释放、载重、速度、电量和避碰能力。地图必须让评委能够直接识别进货、出货、货架巷道、机器人和充电口，并为算法提供多条横纵可选路线。

## 2. 已选方案

设计阶段比较了平行货架巷道型、业务分区型和混合型。最终采用平行货架与功能分区结合的方案：

- 进货点位于地图顶部。
- 出货点位于地图底部。
- 充电口和机器人起点位于右侧。
- 中央由多组 `3 × 2` 货架组成。
- 每个货架、进货点、出货点、充电口和机器人都严格占一个网格单元。
- 所有独立对象或对象组之间统一保留两个完整的空白可走格。
- 所有非障碍单元均可通行，横向和纵向双格通道组成完整连通路网。

不使用跨格功能区、跨格货架图形或脱离单元格边界的道路线条。

## 3. 范围

本次包含：

- 将 `integrated-demo` 从 `14 × 10` 升级为 `26 × 16`。
- 重建障碍、功能点、机器人起点和默认任务坐标。
- 保留场景 ID `integrated-demo`，继续作为唯一前端固定场景和共享后端回归基线。
- 使用现有 `zones.warehouse`、`zones.delivery`、`zones.inspection` 和 `zones.charging`，不新增地图数据字段。
- 在前端按单元格显示进货、出货、巡检和充电语义。
- 调整默认任务截止时间、电量和测试推进时长，使新地图保持稳定可演示。
- 更新固定演示、实验基线、场景数据、前端视图和相关文档测试。

本次不包含：

- 新增第二张主演示地图。
- 默认触发运行时封锁、机器人故障、手工任务或定时生成任务。
- 删除运行时任务、封锁、故障和恢复接口。
- 新增实验面板。
- 修改任务分配、A*、冲突避免、动态重规划、锁、抢占或恢复算法，除非新场景暴露可复现的真实算法缺陷。
- 实现第三级避碰、全规划时域零冲突保证或独立执行安全门。
- 强制主演示实际进入充电流程。

## 4. 坐标系与地图尺寸

地图尺寸为 `width: 26`、`height: 16`。坐标仍使用 `[x, y]`，左上角为 `[0, 0]`，有效范围为：

- `x = 0..25`
- `y = 0..15`

“间隔两格”定义为两个对象边界之间完整存在两个不同的非障碍单元。两条网格边界线不算两格；一个双格宽通道必须包含两个可通行单元。

## 5. 货架与双格通道

每个货架组由 `3 × 2` 个单格障碍组成。货架组列范围为：

- `x = 2..4`
- `x = 7..9`
- `x = 12..14`
- `x = 17..19`

货架组行范围为：

- `y = 3..4`
- `y = 7..8`
- `y = 11..12`

`obstacles` 是以上四个列范围与三个行范围的笛卡尔组合，共 `4 × 3 × 3 × 2 = 72` 个单格障碍。

双格通道固定为：

- 左侧外通道：`x = 0..1`。
- 货架组横向间隔：`x = 5..6`、`10..11`、`15..16`。
- 货架到机器人起点列的间隔：`x = 20..21`。
- 机器人到充电口的间隔：`x = 23..24`。
- 进货点到首排货架的间隔：`y = 1..2`。
- 货架组纵向间隔：`y = 5..6`、`9..10`。
- 末排货架到出货点的间隔：`y = 13..14`。

所有不在 `obstacles` 中的单元均可走。不存在只用于视觉展示、但算法不可进入的道路。

## 6. 功能点与机器人起点

进货点使用 `zones.warehouse`，位于：

```text
[2,0], [5,0], [8,0], [11,0], [14,0], [17,0]
```

相邻进货点之间分别保留两个空格。

出货点使用 `zones.delivery`，位于：

```text
[2,15], [5,15], [8,15], [11,15], [14,15], [17,15]
```

相邻出货点之间分别保留两个空格。

四个机器人起点位于：

```text
R1 [22,3]
R2 [22,6]
R3 [22,9]
R4 [22,12]
```

四个充电口位于：

```text
[25,3], [25,6], [25,9], [25,12]
```

同一行的机器人与充电口之间由 `x = 23..24` 两个可走单元隔开。相邻机器人起点、相邻充电口之间也分别保留两个单元。

机器人继续保留现有角色和差异：`R1`、`R2` 为搬运车，`R3` 为巡检车，`R4` 为备用协作车；载重和 `moveTicks` 差异保持不变。初始电量和 `batteryCapacity` 根据新默认路线校准，但必须满足默认演示不依赖实际充电才能完成的验收条件。

## 7. 默认任务

继续保留六个默认任务和原有任务 ID，不增加主演示任务数量。

### 7.1 取送任务

- `T1`：从左上进货点 `[2,0]` 送往右下出货点 `[17,15]`，保持优先级 `3`。
- `T2`：从右上进货点 `[17,0]` 送往左下出货点 `[2,15]`，保持优先级 `3`。
- `T4`：从中部进货点 `[8,0]` 送往中部出货点 `[11,15]`，保持优先级 `2` 和 `releaseTime: 4`。

`T1` 与 `T2` 形成方向相反的交叉物流，用于制造真实的会车和交叉口调度压力。`T4` 在在线会话运行后释放，继续覆盖滚动重规划和延迟任务加入。

### 7.2 巡检任务

- `T3` 保持优先级 `2`，负责横向双格通道覆盖。
- `T5` 保持优先级 `1` 和 `releaseTime: 8`，负责纵向双格通道覆盖。

横向覆盖目标沿 `y = 1,2,5,6,9,10,13,14` 蛇形排列，右端停在 `x = 24`，不占用 `x = 25` 的充电口列。`T3.targets` 顺序固定为：

```text
[0,1],  [24,1],
[24,2], [0,2],
[0,5],  [24,5],
[24,6], [0,6],
[0,9],  [24,9],
[24,10],[0,10],
[0,13], [24,13],
[24,14],[0,14]
```

纵向覆盖目标沿纯道路列 `x = 0,1,5,6,10,11,15,16,20,21,22,23,24` 蛇形排列，上下端使用 `y = 1` 和 `y = 14`，不与 `y = 0` 的进货点或 `y = 15` 的出货点重合。`T5.targets` 顺序固定为：

```text
[0,1],  [0,14],
[1,14], [1,1],
[5,1],  [5,14],
[6,14], [6,1],
[10,1], [10,14],
[11,14],[11,1],
[15,1], [15,14],
[16,14],[16,1],
[20,1], [20,14],
[21,14],[21,1],
[22,1], [22,14],
[23,14],[23,1],
[24,1], [24,14]
```

以上顺序保证相邻通道通过边缘通道连接，不依赖越过货架或不可达跳转。`zones.inspection` 保存两个巡检任务目标的去重集合；巡检点不得与进货点、出货点、充电口或机器人起点重合。前端不把整条道路误画成一个跨格对象。

### 7.3 默认紧急任务

`E1` 继续作为场景内默认任务，而不是运行时手工任务或 `dynamic.tasks` 项：

- 类型保持 `emergency`。
- 优先级保持 `5`。
- `releaseTime` 保持 `12`。
- 目标使用货架内部通道交叉点 `[11,10]`。
- 不新增独立应急区。

`dynamic` 继续保留合法结构，但 `blockedCells`、`failedRobots` 和 `tasks` 均为空。默认流程不会触发额外动态封锁或故障。

## 8. 时序、电量与截止时间校准

新地图和巡检覆盖路线明显长于旧场景，不能复用旧截止时间和电量数值后直接宣称基线通过。实施时按以下规则校准：

- 保留现有任务优先级、`releaseTime` 和 `serviceTime` 语义。
- 使用开启冲突避免的固定场景运行结果测量每个任务的实际完成时间。
- 截止时间必须晚于稳定基线中的实际完成时间，并保留至少 `20%` 的时间余量；同时不得通过删除巡检目标来满足截止时间。
- 初始电量和容量必须覆盖默认分配结果中的最大移动消耗，并保留至少 `10%` 的容量余量。
- 默认验收中 `chargingVisits` 可以为 `0`；充电闭环继续由专门低电量回归验证。
- 如果任务分配变化会导致某台机器人路线超出电量，优先统一提高场景电池容量和相应初始电量，不改变充电算法。

具体数值由可重复的实现期回归结果确定，并固化到场景 JSON 和测试断言中。

## 9. 前端单格显示

当前地图只为 `zones.charging` 增加专用单元格样式。本次在不改变 API 数据结构的前提下补齐区域显示：

- `zones.warehouse` 单元增加进货背景和“进”语义。
- `zones.delivery` 单元增加出货背景和“出”语义。
- `zones.inspection` 单元增加巡检边框或底色和“巡”语义。
- `zones.charging` 继续显示充电背景和“充”语义。
- 货架继续由 `obstacles` 单格显示。
- 机器人继续由当前位置单格显示。

显示优先级为：机器人标记优先于任务文字；任务文字优先于功能点文字；功能点背景始终保留。运行时封锁、冲突和失败状态继续沿用现有高优先级样式，不得被功能点底色遮蔽。

不得新增跨格区域图层、独立仓库画布或新的场景字段。地图仍由现有 CSS Grid 按 `width` 和 `height` 渲染。

## 10. 在线流程与数据流

场景仍从 `frontend/src/domain/scenarios.json` 加载，经 `frontend/src/domain/scenarios.ts` 导出，并通过现有会话创建请求发送给后端。后端继续使用统一场景校验、会话创建、任务状态、路径规划和事件日志流程。

默认演示仅依赖场景内六个任务。手工任务和定时生成任务仍共用现有运行时任务接口；运行时封锁、机器人故障和恢复 API 仍保留，但不写入默认演示步骤。导入其他场景时，现有动态事件机制继续可用。

## 11. 校验与错误处理

现有前后端场景校验继续负责坐标边界、障碍冲突、机器人 ID、动态失败机器人引用和任务结构。本次增加或强化场景数据回归，明确验证：

- 地图尺寸精确为 `26 × 16`。
- 障碍数量为 `72`，并满足十二个 `3 × 2` 货架组结构。
- 任意相邻货架组的横向和纵向净距均为两格。
- 进货点、出货点、机器人起点和充电口均不与障碍重叠。
- 已确认的功能点和机器人坐标精确匹配。
- 所有非障碍单元构成一个连通分量。
- 六个默认任务目标均合法且可达。
- 横向和纵向巡检目标覆盖约定的全部通道。

不为这张固定地图增加运行时自动修复或坐标容错。共享 JSON 中出现错误时应由测试失败直接阻止提交。
