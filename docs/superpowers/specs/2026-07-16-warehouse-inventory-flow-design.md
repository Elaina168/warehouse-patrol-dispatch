# 仓库货架库存流转与亮灯反馈设计

## 背景

当前 `integrated-demo` 已升级为 `26 × 16` 真实仓库地图，但业务语义仍有偏差：中间 `3 × 2` 货架组仅作为不可通行障碍，默认取送任务直接从顶部进货点送到底部出货点，没有经过货架存取环节。前端也没有货架库存状态，因此无法表现放货后亮灯、取货后恢复的变化。

本次工作修正仓库业务流，同时保持现有在线任务接口、任务类型和核心调度算法不变。

## 目标

- 机器人不能进入货架格，只能在货架唯一相邻作业格完成取放。
- 入库任务必须从进货点取货并送到空货架作业格。
- 出库任务必须从已有货物的货架作业格取货并送到出货点。
- 放货完成后对应货架亮起；取货完成后对应货架恢复普通样式。
- 默认流程通过初始库存同时展示入库和出库，不引入任务依赖。
- 手工任务和随机生成任务继续使用同一个运行时任务接口，并执行同一套库存规则。
- 后端维护权威库存状态，前端不自行推断。
- 不修改任务分配、A*、冲突避免、锁、抢占、故障恢复或充电算法。

## 不在本次范围内

- 不实现货物 SKU、数量、批次、重量或库位容量。
- 不实现一个货架存放多件货物。
- 不增加任务来源字段，不区分手工任务和自动生成任务。
- 不增加任务取消接口；未完成任务的货架预订持续到任务完成或会话重置。
- 不实现第三级全规划时域零冲突保证或独立执行安全门。
- 不改变充电规则、机器人能力模型或现有优先级语义。

## 兼容性策略

保留现有分区字段：

- `zones.warehouse` 继续表示6个进货点。
- `zones.delivery` 继续表示6个出货点。
- `zones.inspection` 继续表示巡检点。
- `zones.charging` 继续表示充电口。

不重命名这些字段，避免无必要地破坏现有场景导入、前后端类型和实验接口。场景新增结构化 `shelves`，会话响应新增 `shelfStates`。

## 场景货架模型

`Scenario` 新增：

```text
shelves: [
  {
    id,
    cell,
    serviceCell,
    initialOccupied
  }
]
```

字段含义：

- `id`：货架唯一标识。
- `cell`：货架实体格；该坐标必须同时存在于 `obstacles`。
- `serviceCell`：机器人完成该货架取放操作的唯一相邻通道格。
- `initialOccupied`：创建或重置会话时，该货架是否已有货物。

货架编号按地图从上到下、从左到右生成稳定 ID。每个货架格和作业格均唯一，不允许两个货架共享作业格。

### 作业格映射

每个货架组保持 `3 × 2`：

- 上排3个货架分别使用正上方通道格。
- 下排3个货架分别使用正下方通道格。

因此每组6个货架均有一一对应作业格，机器人永远不进入货架障碍格。

### 初始库存

每个 `3 × 2` 货架组预置1个有货货架，共12个：

```text
[3,3], [8,3], [13,3], [18,3]
[3,7], [8,7], [13,7], [18,7]
[3,11], [8,11], [13,11], [18,11]
```

其余60个货架初始为空。

## 会话库存状态

后端会话为每个货架维护以下状态：

```text
empty
inboundReserved
occupied
outboundReserved
```

含义：

- `empty`：空货架，可接受入库任务。
- `inboundReserved`：已被入库任务预订，尚未放货，不显示库存高亮。
- `occupied`：已有货物，可接受出库任务，显示库存高亮。
- `outboundReserved`：已被出库任务预订、尚未取货，继续显示库存高亮。

`SessionResult` 新增 `shelfStates`，每项至少包含货架 ID 和当前状态。前端所有库存显示和随机任务候选均以该响应为准。

### 状态变化

```text
empty
  -> 入库任务提交成功
inboundReserved
  -> 放货作业和 serviceTime 完成
occupied
  -> 出库任务提交成功
outboundReserved
  -> 机器人实际到达取货作业格并取得货物
empty
```

出库任务在机器人实际取货时释放货架，不等待机器人到达出货点。若机器人取货后发生故障，货架仍保持空状态，货物继续沿用现有配送载荷连续性规则。

机器人故障、临时封锁或临时不可达只触发重规划，不释放未完成任务的货架预订。会话重置恢复 `initialOccupied`，并清除所有运行时预订和库存变化。

## 取送任务业务识别

取送任务继续使用现有 `delivery` 类型和 `pickup`、`dropoff` 坐标，不新增来源字段或货架 ID 字段。

后端按坐标自动识别：

- 入库：`pickup` 位于 `zones.warehouse`，`dropoff` 等于某个货架的 `serviceCell`。
- 出库：`pickup` 等于某个货架的 `serviceCell`，`dropoff` 位于 `zones.delivery`。
- 其他组合：不是合法仓库取送任务，拒绝场景或运行时请求。

场景自带任务、手工任务和随机生成任务执行相同规则。

### 库存校验与预订

- 入库只能选择 `empty` 货架；任务提交成功后立即转为 `inboundReserved`。
- 出库只能选择 `occupied` 货架；任务提交成功后立即转为 `outboundReserved`。
- `inboundReserved` 和 `outboundReserved` 均不能被第二个任务重复选择。
- 初始场景任务在创建会话时按相同规则建立预订。
- 不合法的运行时任务返回 `422`，且不得改变库存状态、任务数量、会话时间、指标历史或当前规划。

错误详情需要明确区分：

- 不是合法的进货点到货架作业格组合。
- 不是合法的货架作业格到出货点组合。
- 入库货架已有货物或已被预订。
- 出库货架为空或已被预订。
- 作业格没有对应货架。

## 默认六任务流程

保留任务 ID、类型数量、优先级、作业时间、释放时间和当前校准截止时间，只调整3个取送任务坐标：

- `T1` 入库：进货点 `[2,0]` -> 货架 `[2,4]` 的作业格 `[2,5]`。
- `T2` 出库：初始有货货架 `[13,7]` 的作业格 `[13,6]` -> 出货点 `[2,15]`。
- `T4` 入库：进货点 `[8,0]` -> 货架 `[12,8]` 的作业格 `[12,9]`。
- `T3`：保持横向巡检目标不变。
- `T5`：保持纵向巡检目标不变。
- `E1`：保持目标 `[11,10]`、`T=12` 释放和应急语义不变。

默认流程不自动生成任务、不自动封锁单元、不自动标记机器人故障，也不要求触发充电。

预实施只读探测已经确认上述坐标满足以下固定输入结果。实现后必须重新测量；若库存状态接入本身改变结果，应停止并检查库存实现，不修改避碰算法：

- 无避碰基线预测冲突大于0。
- 开启避碰后6个任务全部分配，预测冲突为0。
- 默认在线流程在 `T=700` 前完成6个任务，失败、截止超期和充电访问均为0。

## 随机任务生成

前端随机生成器读取最新 `shelfStates` 构造取送候选：

- 同时存在 `empty` 和 `occupied` 候选时，入库和出库各约50%。
- 只有 `empty` 候选时，只生成入库。
- 只有 `occupied` 候选时，只生成出库。
- 没有合法取送候选时，本轮改生成巡检或应急任务。
- 入库随机选择一个进货点和一个空货架作业格。
- 出库随机选择一个已有货物货架作业格和一个出货点。

前端候选过滤用于避免明显无效请求，后端统一任务接口仍执行最终库存校验。随机任务和手工任务继续提交到同一个 `POST /api/sessions/{session_id}/tasks`，并沿用现有生成任务 ID 规则和 `runtimeTaskCount` 统计。

## 前端显示

地图继续把货架格渲染为不可通行障碍。

- `empty` 和 `inboundReserved`：普通深色货架样式。
- `occupied` 和 `outboundReserved`：显示明亮库存高亮。
- 入库放货完成后高亮出现。
- 出库实际取货后高亮消失。
- 机器人显示在相邻作业格，不覆盖货架。
- 任务格文字继续优先显示“取”“送”“巡”“急”，区域底色继续表达进货、出货、巡检和充电语义。

货架应提供可读状态信息，使人工测试能识别货架 ID、作业格和当前库存状态。主界面不增加独立实验面板或营销式展示面板。

## 场景与运行时校验

场景校验新增：

- 货架 ID、货架格、作业格不得重复。
- 货架格和作业格必须位于地图范围内。
- 货架格必须存在于 `obstacles`。
- 作业格必须与货架格曼哈顿距离为1。
- 作业格不能是固定障碍或当前生效的动态封锁。
- 默认入库任务只能预订初始空货架。
- 默认出库任务只能预订初始有货货架。
- 同一货架不能被两个未完成默认任务同时预订。

运行时拒绝请求必须保持非变更语义，不写入任务、库存、会话时间、最后规划结果、指标历史或分配偏好。

## 测试与验收

### 场景和契约

- `integrated-demo` 恰好包含72个货架、72个唯一作业格和12个初始有货货架。
- 每个货架格存在于 `obstacles`，每个作业格可通行且唯一。
- 前后端 `Scenario`、货架模型、`SessionResult.shelfStates` 和状态字面量保持一致。
- 场景导入、导出和 OpenAPI 契约覆盖新增字段。

### 库存状态

- 创建会话后，12个初始货架显示库存，其中默认 `T2` 对应货架为 `outboundReserved`。
- 默认 `T1`、`T4` 对应空货架为 `inboundReserved` 且不亮。
- 入库完成后对应货架变为 `occupied` 并亮起。
- 出库到达取货作业格后对应货架变为 `empty` 并熄灭。
- 机器人故障、恢复和动态重规划期间预订保持一致。
- 出库取货后机器人故障时，货架保持空状态，配送载荷连续性不回退。
- 会话重置后恢复12个初始有货货架。

### 统一任务接口

- 手工和随机入库只能使用空货架。
- 手工和随机出库只能使用已有货物货架。
- 重复预订返回 `422`，并验证会话无副作用。
- 随机生成器不会选择空货架出库或已预订货架。
- 无合法取送候选时生成巡检或应急任务。

### 默认流程与实验

- 默认6任务在 `T=700` 前全部完成。
- 冲突、失败、截止超期和充电访问均为0。
- 最终有货货架数量为13：初始12个，`T2` 取走1个，`T1`、`T4` 放入2个。
- 无避碰基线预测冲突大于0，开启避碰后预测冲突为0。
- 滚动窗口、动态变体、规模实验和固定端到端回归继续通过。

### 前端和人工验收

- 前端纯函数测试覆盖货架状态到 CSS 类和可读标签的映射。
- 随机候选测试覆盖空货架、有货货架、预订货架和无候选回退。
- 前端构建和全部前后端测试通过。
- 启动平台后确认初始12个货架高亮。
- 播放默认流程时确认 `T2` 取货后对应货架熄灭，`T1`、`T4` 放货后对应货架点亮。
- 地图单元和路径层继续对齐。
