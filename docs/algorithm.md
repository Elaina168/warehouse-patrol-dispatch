# 调度算法说明

本文档记录当前已经实现并通过测试的调度规则，用于稳定化和展示验收。

截至 2026-08-30，本文档只描述已经进入主线的算法与运行时规则。当前没有选定下一项算法升级；离线基准和自适应校准仅提供内部诊断证据，不自动形成生产改动。

## 调度入口

- 批量调度入口：`POST /api/dispatch`
- 在线会话创建：`POST /api/sessions`
- 在线会话列表：`GET /api/sessions`
- 在线会话详情：`GET /api/sessions/{session_id}`
- 在线会话删除：`DELETE /api/sessions/{session_id}`
- 在线会话重置：`POST /api/sessions/{session_id}/reset`
- 在线任务追加：`POST /api/sessions/{session_id}/tasks`
- 运行中新机器人接入：`POST /api/sessions/{session_id}/robots`
- 运行中机器人永久退役：`POST /api/sessions/{session_id}/robots/remove`
- 会话时间推进：`POST /api/sessions/{session_id}/tick`
- 运行时封锁：`POST /api/sessions/{session_id}/blocked-cells`
- 解除运行时封锁：`POST /api/sessions/{session_id}/blocked-cells/remove`
- 机器人故障：`POST /api/sessions/{session_id}/failed-robots`
- 恢复机器人：`POST /api/sessions/{session_id}/failed-robots/restore`

核心计算位于 `backend/app/dispatch.py`，在线状态推进位于 `backend/app/sessions.py`。

## 任务分配

任务分配使用 beam search：

- 候选宽度按机器人数量动态设置，当前为 `max(8, min(48, len(active_robots) * 12))`。
- 任务基础排序按优先级、截止时间、释放时间和任务 ID 排列。
- 机器人候选会考虑任务距离、等待时间、截止时间迟到惩罚、低电量惩罚、总距离和负载均衡。
- 不可用机器人不会参与分配。
- 机器人必须声明支持任务类型；配送任务还必须满足 `robot.load >= task.demand`。能力或载重硬约束不能被距离、速度、优先级、锁定或软偏好覆盖。

任务优先级是闭区间 `0..5`，数值越大越优先：

| 数值 | 语义 |
| --- | --- |
| `0` | 普通/后台 |
| `1` | 低 |
| `2` | 正常 |
| `3` | 高 |
| `4` | 紧急 |
| `5` | 最高/应急 |

突发任务的优先级至少为 `4`，随机突发任务只生成 `4` 或 `5`。抢占只考虑严格更高优先级的任务；同优先级任务不会释放现有锁。负数优先级和大于 `5` 的值会在请求模型校验阶段被拒绝。

## 任务类型能力与载重

`Robot.capabilities` 只允许以下三个精确值：

```text
inspection
delivery
emergency
```

旧场景省略 `capabilities` 时，后端默认该机器人支持全部三种任务；显式提供时必须是非空、无重复值的合法子集。默认 `integrated-demo` 的四台机器人均显式配置为 `["inspection", "delivery", "emergency"]`，因此主演示仍是全能力车队，不通过专业分工改变既有六任务结果。

统一资格判断先检查任务类型是否在 `capabilities` 中，再对配送任务检查 `robot.load >= task.demand`。当前默认、手工和随机配送任务继续使用 `demand: 1`；本功能不增加重量单位、多级货物或动态载重。任务类型不兼容和配送载重不足使用不同失败说明。

## 运行中新机器人接入

在线会话可以在当前任意 tick 暂停后接入机器人。请求体包含完整的 `robot` 配置（`id`、`name`、`start`、`battery`、`batteryCapacity`、`load`、`moveTicks`、`capabilities`），以及可省略的 `currentTime`；省略时后端使用会话当前时间，显式过去时间会被拒绝。

接入在同会话锁内使用候选副本完成：候选副本先推进到请求时间，再检查机器人总数不超过 `MAX_SCENARIO_ROBOTS = 32`、ID 唯一、坐标在地图内且不位于固定障碍、货架实体格、当前封锁格或其他机器人当前占用格。普通可通行格、空闲充电格和可通行作业格可以作为接入位置；机器人自身的 Pydantic 约束（能力至少一项且无重复、电量不超过容量、载重和 `moveTicks` 范围等）继续生效。只有候选完成加入、初始化、旧计划失效、重规划和结果构建后才发布；校验、重规划或结果构建失败都不改变权威会话的时间、路径、指标、事件和缓存。

初始机器人保存 `joinedAt = 0`，运行时机器人保存真实接入 tick。`SessionResult.robotStates` 对每台当前机器人返回完整配置、当前位置、运行状态、电量、载重、能力和 `joinedAt`；`DispatchResult.pathStartTimes` 标记路径的绝对起点。运行时机器人的路径历史和累计距离从接入时刻开始，历史回放在接入前不会显示它，也不会把接入位置伪造为 T=0 的历史。接入事件以 `T=<time> 新机器人接入：<id> <name>` 写入事件日志。

接入后机器人直接参与既有启发式分配、A*、时空预约避碰、冲突检测、动态重规划和执行安全门；它也复用现有故障与恢复接口。新任务或规则允许重新分配的待执行任务可以被它接管，已取货配送任务仍遵循原有货物进度和锁语义。`reset` 恢复初始场景、移除运行时机器人，并将初始机器人接入时间恢复为 `0`。该功能不代表任意输入下的零冲突保证、完整 MAPF/CBS、实体通信或边缘端部署。

## 运行中机器人永久退役

在线会话通过 `POST /api/sessions/{session_id}/robots/remove` 申请永久退役，请求模型为 `RemoveRobotRequest`：`robotId` 必填，`currentTime` 可省略；省略时使用会话当前 tick，显式过去时间会被拒绝。这里的“永久”表示在当前会话生命周期内不再回到调度池，不是删除历史数据；`reset` 才会恢复初始场景中的机器人集合。

退役校验只允许以下安全状态：真正 `idle` 的机器人；只有未锁定远期任务的 `waiting` 机器人；或任务已经完成移交、没有携货进度的 `failed` 机器人。以下情况会拒绝：正在执行任务（`toPickup`、`delivering`、`inspecting`）、已取货但尚未送达、存在未完成硬锁定任务、正在前往充电或充电中，以及移除后没有其他可用活动机器人。故障机器人只有在任务已移交且不再携货时才满足第一版条件。

退役操作在同一会话锁内对候选副本执行：先推进到请求时间，再检查上述状态，记录 `removedAt`，从后续有效机器人集合中排除并完成重规划和结果构建；全部成功后才提交候选。任一校验、重规划或结果构建失败，权威会话的时间、路径、任务状态、指标历史、事件、缓存和偏好都不变。重复退役请求返回当前结果，不新增事件；同一会话内即使机器人已退役，其 ID 仍占用，不能再次接入。故障标记和故障恢复接口都拒绝 `removed` 机器人。

`RobotRuntimeState` 仍保留被退役机器人，并返回 `status: "removed"`、`joinedAt` 和绝对 `removedAt`。时间语义是 `joinedAt <= T < removedAt` 时存在，`T >= removedAt` 时隐藏并不再参与规划、任务分配、冲突预测或执行安全门；`result.paths` 保留截至退役时的历史路径，指标历史与事件日志保留退役前记录，前端历史回放可以查看退役前轨迹。`reset` 清除退役时间和运行时机器人状态，恢复原始四台机器人（对于初始场景含四台时）。

## 机器人移动速度

机器人可配置 `moveTicks`，表示移动一格需要的整数 tick，取值为 `1` 到 `4`。旧场景缺失该字段时按 `1` 处理，保证既有导入场景和调度 API 可继续运行。

- 任务分配按网格距离乘以该机器人的 `moveTicks` 计算移动耗时，因此同等距离时会优先选择更快的机器人。
- 时间路径把一次移动展开为中间占用 tick。例如 `moveTicks=3` 从 A 到 B 的路径为 `[A, A, A, B]`。
- 避碰预约会检查中间 tick 的出发格占用、到达格顶点预约和反向边预约；慢速机器人占用通道更久时，其他机器人会等待或绕行。
- `serviceTime` 只在到达任务最后一个目标后追加，不受移动速度影响。
- 前端播放速度只控制请求 tick 的频率，不改变后端 `moveTicks` 调度语义。

## 电量与充电

带充电格的场景会启用硬电量约束：

- 机器人每跨越一个相邻网格消耗 `1` 点电量。
- `moveTicks` 只改变一格移动占用的 tick 数，不改变单格耗电量。
- `serviceTime` 表示到达任务最终目标后的作业停留，不消耗电量。
- `Robot.batteryCapacity` 缺失时默认为 `100`，且运行时 `battery` 不得超过容量。
- `Scenario.chargeTime` 缺失时默认为 `4`，表示一次完整充电等待的 tick 数。

如果 `zones.charging` 非空，调度器只会分配“当前电量足以完成任务并在任务结束后到达可达充电格”的任务。当前电量不足但机器人还能到达充电格时，后端会先规划前往充电格，充电完成后再继续任务；`toCharge` 和 `charging` 状态下的机器人不会被新任务抢占。

如果运行时封锁导致通往充电格的路线不可达，任务会保持临时失败或等待恢复，并通过 `failureDetails.recoveryAction = "clearBlockedCells"` 暴露需要清除的封锁单元。缺少充电格的旧场景按兼容模式处理：仍检查当前剩余电量能否覆盖任务移动距离，但不强制任务结束后返航充电。

## 执行不变量

- 最终生成的 timed path 是实际移动与电量消耗的权威来源。分配阶段的距离和电量估计只用于筛选；时空避碰绕行、充电路径和任务结束后的停车移动都按最终路径中的跨格次数再次校验，等待、慢速移动的中间占用 tick 和作业停留不扣电。
- 在线推进会在写入 `robot_path_history` 前检查最终路径的下一次跨格移动。若当时电量已为 `0`，全车保持原位、记录电量安全门事件并使当前计划失效，不会把零电量移动写入路径历史。
- 场景校验要求所有机器人起点唯一；重复起点会以 `机器人起点重复：(x, y)` 拒绝直接调度和在线会话创建。
- 指定未来 `currentTime` 的运行时封锁先在深拷贝的会话候选上推进和验证，只有整项操作成功才提交。占用冲突等拒绝结果不会修改会话时间、`updatedAt`、计划缓存、指标历史或分配偏好，也不会部分提交候选中的运行时状态。
- T=0 即时完成与正常 tick 共用任务完成、出库取货和入库放货转换；完成任务会清理锁与分配偏好，库存状态和事件只转换一次，然后重规划到不含已完成任务的最终结果。
- `MAX_PLANNED_PATH_TICKS = 10_000` 限制从 T=0 起的完整计划时域，因此单条路径最多包含 `10,001` 个节点。释放等待、充电等待、`serviceTime`、时空 A* 段和停车段都受同一累计上限约束；超限任务返回 `规划路径超过最大时域 10000 tick`、`category = "permanent"` 和 `recoveryAction = "fixTaskDefinition"`。

这些不变量限制执行与资源边界，但不把当前优先级时空 A* 提升为完整 MAPF/CBS 求解器，也不保证任意输入都有零冲突解。

## 滚动窗口

当前分配器使用可配置滚动窗口：

- 默认值：`DispatchOptions.assignmentReplanWindow = 24`
- 允许范围：`0` 到 `120`
- `DispatchOptions.adaptiveReplanWindow = false` 时保持固定窗口，兼容既有场景和回归。
- 开启自适应后，`assignmentReplanWindow` 表示基准窗口，实际窗口限制在 `4` 到 `120`。
- 自适应延迟反馈在至少有 3 个真实重规划样本后，使用最近 5 个样本的中位数：中位数达到 `60ms` 进入慢状态，已处于慢状态时中位数降至 `40ms` 才退出；慢状态或已释放任务达到可用机器人数量两倍时，窗口收缩到基准值的一半。没有已释放任务但存在远期任务时，窗口扩大到基准值的两倍；其他情况保持基准值。
- 非锁定任务中，释放时间在窗口内的任务优先参与排序。
- 释放时间超过窗口的远期任务会排在当前窗口任务之后。
- 在线会话使用本轮实际窗口计算 `T=<time> 滚动窗口纳入远期任务` 的触发 tick。
- `DispatchResult.effectiveAssignmentReplanWindow` 和 `replanWindowReason` 分别返回实际窗口和决策原因。

这个规则用于避免远期高优先级任务过早扰动当前执行计划。

### 自适应策略与观测边界

`AdaptiveReplanPolicy` 是后端内部不可变策略对象，不属于 Pydantic 请求模型、HTTP 路由字段或前端类型，HTTP 调用方不能传入或覆盖。生产入口继续调用默认的 `create_session(request)`，不注入策略或 observer；当前默认值保持为：

- 慢状态进入阈值 `60ms`。
- 慢状态退出阈值 `40ms`。
- 最近 `5` 个真实重规划样本，至少 `3` 个样本后才更新慢状态。
- 已释放任务压力阈值为可用机器人数量的 `2×`。

内部 observer 只在会话确实调用一次 `run_dispatch` 后记录 `ReplanObservation`，同时记录该次真实重规划的窗口决策、耗时和确定性规划工作量。延迟初始规划的 idle 响应、复用 `last_result` 的缓存响应和不触发重规划的被动 tick 不产生观测；开启 observer 只增加诊断采集，不改变调度结果、候选顺序、固定窗口语义或在线执行安全。`adaptiveReplanWindow = false` 仍直接使用配置窗口，缓存和被动推进仍复用既有计划。

离线自适应窗口校准中的墙钟耗时只用于同一机器、无并发重型任务时的人工比较。报告中的候选范围是供后续单独审批决策使用的证据，不会自动写回生产配置；在另行批准并验证生产改动前，`60/40ms`、最近 `5` 个样本且至少 `3` 个样本、`2×` 压力规则均保持不变。该校准不证明跨机器阈值可移植性，也不证明完整 MAPF 或任意输入下的全规划时域零冲突。

2026-07-26 修复前的默认 60-run 同机复核中，低负载与过渡案例的全部变体均稳定，但压力案例的全部变体均出现相同的任务覆盖、截止时间和失败问题；因此报告没有产生候选 envelope。该 completed-but-unstable 结果作为历史诊断原样保留。校准 fixture 修复后的 fresh 60-run 全部 completed 且 stable，并产生了非空同机候选范围；它仍没有自动修改生产策略。最新 fresh 结果目录为 `output/adaptive-replan-calibration/20260726T150547Z`，其同机候选范围依次为慢状态退出 `9.71–31.05ms`、进入 `31.05–69.47ms`、任务压力倍数 `1.75–3.38`；这些值仅是证据，不应用于生产阈值。

## 锁定任务

在线会话推进时，已经开始执行且尚未完成的任务会锁定到当前机器人。

锁定规则：

- 锁定任务只有在原机器人能力与配送载重仍匹配时才继续分配给原机器人；不兼容锁不能覆盖能力硬约束。规划前发现类型不兼容或载重不足的陈旧锁时，仅在另有当前可用、可达且电量可行的机器人能够执行任务时删除该锁并在同次规划中改派；在线会话同时记录释放原因。
- 锁定任务在分配排序中作为前缀处理，防止新任务插到已锁定任务之前。
- 任务完成后会从锁定表中移除。
- 原机器人静态资格合法但暂时故障、受封锁影响或电量不足时，不由上述陈旧锁清洗逻辑删除，继续沿用故障、封锁、电池与抢占的既有恢复流程。

释放规则：

- 机器人故障时，释放该机器人持有的锁定任务。
- 新封锁单元影响未来锁定路径时，释放受影响锁定任务。
- 已到达的高优先级任务会触发抢占试算；只有释放低优先级锁后评分更优，才真正释放。
- 正在前往充电或充电中的机器人不会释放当前锁定任务给新任务抢占。

## 抢占评分

高优先级任务到达后，会比较两个方案：

- 保留当前锁定任务。
- 释放低优先级锁定任务。

评分顺序为：

1. 触发任务是否完成。
2. 触发任务迟到量。
3. 触发任务完成时间。
4. 全局截止时间未达成数量。
5. 失败数量。
6. 冲突数量。
7. 平均迟到。
8. makespan。
9. 总距离。

只有释放方案评分严格更好时，才释放低优先级锁定任务。

## 路径规划

路径规划使用 A* 和时空预约：

- 普通距离计算使用 A*。
- 避碰模式下，路径段使用带时间维度的 A*。
- 规划后会记录顶点预约和边预约，用于降低机器人之间的时空冲突。
- 路径规划会尝试多种机器人规划顺序，并按失败数、冲突数、截止时间、makespan、总距离和负载均衡选择最优候选。

## 动态事件

在线会话支持以下运行时事件：

- 手工新增任务。
- 前端定时自动生成任务。
- 手动封锁单元。
- 手动解除封锁单元。
- 机器人故障。
- 机器人恢复。
- 机器人永久退役。

封锁单元不能越界，不能重复封锁固定障碍，也不能封锁当前被机器人占用的单元。

手工新增和定时自动生成的任务都通过 `POST /api/sessions/{session_id}/tasks` 进入同一队列，不区分第二套任务接口或来源字段。每次成功插入统一增加会话响应中的 `runtimeTaskCount`。

如果场景中根本没有支持任务类型的机器人，运行时任务定义会被拒绝并返回 `422`。如果存在兼容机器人但它当前故障或被运行时封锁阻断，任务可进入队列并通过 `failureDetails` 暴露临时恢复条件。前端随机生成器对巡检和突发任务使用车队能力并集；随机配送固定为 `demand: 1`，只有至少一台支持配送且 `load >= 1` 的机器人存在时才进入候选。后端仍是最终验证权威。

运行时更新请求的 `currentTime` 可以省略；省略时后端使用会话当前 tick。显式传入早于会话当前 tick 的时间仍会被拒绝，避免回退在线状态。

如果同一个封锁单元或故障机器人已经由场景动态事件激活，手动重复封锁或重复标记故障会按幂等请求处理，不会增加 `runtimeEventCount`，也不会写入重复的手动事件日志。已激活动态封锁单元的重复手动封锁会跳过普通机器人占用拒绝，确保请求保持无操作语义。

自动任务流使用 `A<n>` 编号；如果场景、动态任务或手动任务已占用某个编号，后端会跳到下一个未占用编号，避免重复任务 ID 干扰任务状态和事件日志。

如果场景动态事件和滚动窗口纳入远期任务发生在同一个 tick，事件日志会同时保留两类触发原因，便于回放时判断本次重规划是否由多个运行时条件共同触发。

## 会话生命周期

在线会话在内存中保存持续调度状态：

- `createdAt`、`updatedAt`、`lastAccessedAt` 用于区分创建、状态更新和最近访问时间。
- 空闲会话会按 `SESSION_TTL_SECONDS` 清理。
- 会话总数超过 `MAX_SESSIONS` 时，会按最近访问时间裁剪最久未访问的会话。
- 单个会话的指标历史按 `MAX_METRICS_HISTORY_SNAPSHOTS` 保留最近快照。
- 运行时事件备注按 `MAX_SESSION_EVENT_NOTES` 保留最近事件。
- 会话时间受 `MAX_SESSION_CURRENT_TIME` 限制，防止无界 tick 增长。
- 会话任务总量受 `MAX_SESSION_TASKS` 限制，包含初始任务、场景动态任务和通过统一任务接口插入的运行时任务。

场景动态事件触发后，即使后续运行时事件超过 `MAX_SESSION_EVENT_NOTES` 并裁剪旧备注，事件日志仍会恢复 `T=<triggerTime> 场景动态事件触发`、原始动态封锁数量和动态故障机器人历史。

动态任务的有效释放时间不会早于 `dynamic.triggerTime`；即使动态任务自身带有更早的 `releaseTime`，在线会话在动态事件触发前仍保持 `pending`，会话返回的任务对象与任务状态保持同一个释放时间，直接调度路径也不会在动态事件前出发。仍处于 `pending` 的任务不会计入后端 `deadlineMissCount` 或前端实时超期数。

滚动窗口纳入远期任务的触发 tick 会作为会话状态保留；即使对应运行时备注被裁剪，事件日志仍会恢复 `T=<time> 滚动窗口纳入远期任务`，避免长会话回放时丢失远期任务进入当前计划的原因。

`reset` 会恢复初始场景和初始选项，清空运行时封锁、机器人故障、手动任务、自动任务、锁定关系、指标历史和事件备注，并允许原始动态事件在同一绝对会话时间再次触发。

## 指标与失败

当前指标包括：

- makespan
- totalDistance
- conflictCount
- loadBalance
- assignedTaskCount
- deadlineMissCount
- averageLateness
- failureCount
- replanTimeMs

`DispatchResult.metrics.totalDistance` 表示当前调度计划中各机器人相邻坐标实际变化次数之和；释放、服务、充电、避碰和慢速移动产生的原地等待 tick 不计入距离。该值会随重规划替换当前计划，不能当作在线会话从开始到结束的累计行驶距离。`Metrics.makespan` 使用时间展开路径的最长 tick 数，包含这些等待。`Metrics.loadBalance` 表示各机器人计划移动距离的均衡程度。`MetricSnapshot.travelledDistance` 才表示会话执行到该 tick 时基于实际路径历史累计的移动距离。

离线自适应窗口校准的 run 级 `totalDistance` 只读取终止时最后一条 `MetricSnapshot.travelledDistance`。若会话结束时 `metricsHistory` 为空，runner 必须将该运行记为 `error` 并完成会话清理；不得读取当前计划的 `DispatchResult.metrics.totalDistance`，也不得以 `0` 回退并把运行标为 `completed`。

未分配任务会计入 `failureCount`，并写入事件日志，避免调度失败被静默忽略。

任务失败详情通过 `failureDetails` 暴露：

- `category` 区分 `temporary` 与 `permanent`。
- `recoveryAction` 给出恢复方向，例如清除封锁、恢复机器人、解除锁后重规划或修正地图/任务定义。
- `blockingCells` 和 `blockingRobotIds` 提供结构化恢复条件，前端不需要解析中文事件文本。

能力相关失败按以下顺序解释：先判断是否存在支持任务类型的机器人，再检查配送载重；随后才判断兼容机器人故障、运行时封锁、锁定和地图可达性。无类型兼容机器人属于永久失败，恢复动作是 `addCapableRobotOrChangeTaskType`；类型兼容但配送载重不足仍沿用增加载重机器人或降低 `demand` 的永久恢复建议。只有兼容且载重合格的故障机器人才能进入 `blockingRobotIds`。恢复时应先恢复不兼容机器人验证失败不变，再恢复唯一兼容机器人触发重规划；运行时封锁则只报告实际阻断兼容机器人的单元。直接调度会按任务释放时间应用延迟动态约束：释放时间达到动态触发 tick 的失败任务使用未来故障和封锁进行原因分类，触发前基础任务仍只使用当前约束，响应顶层 `unavailableRobotIds` 与 `extraBlocked` 不会提前暴露未触发状态。

## 离线小规模可解性参照

为区分“场景在给定运动模型下无解”和“当前优先级规划器没有找到路径”，项目提供独立的离线小规模参照工具。它使用与业务 `Scenario` 分离的固定起点—目标案例：每台机器人从 T=0 同步出发，每个 tick 只能等待、上、右、下或左移一步；联合动作同时禁止顶点冲突和反向边交换冲突。机器人首次到达自己的目标即完成该目标，之后可以继续移动到安全的最终停车位置。

参照求解器是联合状态 A*。搜索状态由所有机器人当前位置和已完成目标位掩码组成，启发式为尚未完成目标的机器人到各自目标的最大曼哈顿距离，目标是最小 makespan。它只接受严格受限的小输入：地图宽、高均为 `1..5`，总格数不超过 `25`，机器人数量为 `1..4`；固定障碍、起点和目标也必须满足案例模型的不变量。

`max-expanded-states` 是精确参照的硬资源上限。开放集耗尽时才返回 `unsolved`；达到扩展上限时返回 `limit`，`limit` 不等于无解，也不能据此形成可解性结论。超时和进程异常同样是独立的运行结果，不应伪装成 `unsolved`。

差分比较不比较任务分配能力：适配器把同一小案例转换成内部业务场景，为每台机器人建立一个单目标巡检任务，并使用固定的 `Assignment` 调用 `backend.app.dispatch.build_paths(scenario, scenario.robots, assignments, True, [], [])`，再用现有冲突检测和目标访问条件判定生产侧路径是否有效。因此结果只反映固定分配下的当前路径规划能力。

该工具是离线算法研究和反例取证能力，不进入在线会话、前端或生产调度链路；它不实现 CBS，不替换现有优先级时空 A*，也不改变当前执行安全门、规划质量或全规划时域安全保证的边界。

当前生产路径规划器在候选评分前增加了一个有限窗口局部联合修复切口：候选存在冲突时取首个冲突的连通分量；候选只有无结构化失败详情的路径失败时，则取所有已分配任务的机器人作为参与者，带结构化 `failureDetails` 的失败不进入该切口。参与机器人最多 3 台；只要存在冲突，首个冲突必须不晚于 T=12；每台参与机器人必须只有一个 T=0 释放、零服务时长的 inspection 目标、单位步长，且场景没有充电、动态事件或运行时封锁。局部联合 A* 最多搜索 12 tick、扩展 20,000 个状态，同时固定未参与机器人的路径，并继续禁止顶点冲突和反向边交换冲突；找不到严格减少冲突或消除普通路径失败的结果时保留原候选。该切口不是完整 MAPF/CBS，也不改变不满足这些条件的生产规划行为。

固定种子案例 `generated-s20260904-i0007` 已转为回归；同一有限切口也通过固定回归修复了 `generated-s20260904-i0009`、`generated-s20260904-i0020` 和 `generated-s20260904-i0034`。默认 68-case 重跑中四个案例均为 `agreementSolved`，但这只覆盖已复核的小规模输入，不能推断任意输入都获得全时域零冲突保证。

## 当前边界

- 当前不是完整 MAPF/CBS 求解器，冲突处理采用时空 A* 加多候选规划顺序。
- 时空 A* 在搜索前检查目标格从曼哈顿最早到达时刻到旧搜索允许的真实最晚目标到达时刻（`max_time + move_ticks - 1`）的顶点预留；仅当该闭区间每个目标时间槽都已被预留时，才以 `goalFullyReserved` 零状态展开返回并尝试下一个机器人规划顺序。
- 该剪枝只证明当前预留表和当前搜索时域下不存在目标到达时间槽；它不证明任意边预留、动态障碍或 MAPF 输入全局无解。
- 一级执行安全（已实现、代码强制）：开启避碰的在线会话会在首个预测顶点或反向边冲突 tick 让全车安全等待，不把冲突动作写入实际路径历史；因此已经执行到的每个 tick 不允许出现同格顶点冲突或反向边交换冲突。
- 二级规划质量（已实现）：固定种子压力回归要求预测冲突为 `0`；`integrated-demo` 的避碰方案要求比基线预测冲突更少，并在冲突到达实际执行 tick 前通过滚动重规划消解。
- 大跨度 tick 请求在首个危险 tick 提前返回；`SessionResult.safetyIntervention` 提供绝对时间、冲突类型、机器人和单元格。前端据此暂停播放并高亮冲突单元和涉及机器人。
- 连续安全停滞是活性诊断，不是新的寻路器。相同规范化冲突连续拦截三次后，系统仍保持全车等待并继续允许重新规划；该状态不证明场景无解，也不提供完整 MAPF 或全时域可达性保证。
- 基线对比、直接调度和实验接口仍可返回或执行预测冲突，用于对照；安全门只属于开启避碰的在线执行链路。

同机 density x5 优化证据中，`medianReplanTimeMs` / P95 分别为：`density-r8-t31` 150.85 / 155.90 ms、`density-r8-t43` 213.56 / 214.37 ms、`density-r8-t55` 231.33 / 235.45 ms。墙钟数据只用于同机、无并发重型任务时的人工比较；扩展状态数才是确定性规划工作量指标。
- 三级完整安全（未实现）：全规划时域零冲突保证仍属于后续独立算法升级。未来路径目前是预测结果，任务完成、封锁、故障和任务到达都会触发重规划。
- 任务类型能力约束只收紧机器人资格，不实现也不声称实现上述全规划时域零冲突保证；该保证与本功能无关。
- 自适应窗口目前使用可解释的分段规则，不从历史记录拟合策略；它使用最近 5 个真实重规划样本，至少 3 个样本后以中位数 `>=60ms` 进入慢态、`<=40ms` 退出，介于两者之间保持当前状态。生产继续使用 `60/40ms` 迟滞和两倍任务压力规则；任何修改都需要另行确认并验证，不能直接采用同机校准候选范围。
- 离线自适应窗口校准只给出同机候选范围和确定性规划工作量证据，不自动推荐或应用阈值；生产策略改动仍需单独批准和完整验证。
- 高优先级抢占只释放低优先级锁定任务，不处理同优先级抢占。
- 前端目前主要消费结果和状态，算法计算集中在后端。
- 已知算法边界用于约束声明和辅助后续决策，不代表已经选择了下一项算法工作。
